PLONKish / AIR 算術化

核心概念

PLONKish 是 PLONK 及其變體（如 Halo2、UltraPLONK）使用的算術化格式，透過自定義門（custom gates）和查表（lookup arguments）提供比 R1CS 更靈活的約束表達能力[1]。AIR（Algebraic Intermediate Representation）是 STARK 系統使用的類似概念。

PLONKish 基礎

表格結構

PLONKish 將計算組織為二維表格[1]：

表格結構：
  行（rows）：n 行，對應電路的 n 個「門」
  列（columns）：k 列，包含不同類型的值

列類型：
  - Advice columns：私密見證值
  - Instance columns：公開輸入/輸出
  - Fixed columns：電路定義的常數（選擇器）
  - Selector columns：啟用/禁用特定門

範例表格（3 列 advice，2 列 selector）：
  Row | a    | b    | c    | s_mul | s_add
  ----|------|------|------|-------|-------
  0   | x    | y    | z    | 1     | 0
  1   | z    | w    | out  | 0     | 1
  ...

門約束（Gate Constraints）

PLONKish 允許定義任意多項式約束[1]：

標準 PLONK 門：
  q_L · a + q_R · b + q_O · c + q_M · (a·b) + q_C = 0

其中：
  a, b, c：當前行的 advice 值
  q_L, q_R, q_O, q_M, q_C：選擇器（fixed 值）

門配置範例：
  乘法門：q_M = 1, q_O = -1, 其他 = 0
    → a · b - c = 0 → a · b = c

  加法門：q_L = 1, q_R = 1, q_O = -1, 其他 = 0
    → a + b - c = 0 → a + b = c

  常數門：q_L = 1, q_C = -k, 其他 = 0
    → a - k = 0 → a = k

自定義門（Custom Gates）

PLONKish 擴展允許更複雜的門[2]：

Halo2 自定義門範例：

// 三元乘法門：a · b · c = d
meta.create_gate("triple_mul", |meta| {
    let a = meta.query_advice(advice[0], Rotation::cur());
    let b = meta.query_advice(advice[1], Rotation::cur());
    let c = meta.query_advice(advice[2], Rotation::cur());
    let d = meta.query_advice(advice[3], Rotation::cur());
    let s = meta.query_selector(s_triple);

    vec![s * (a * b * c - d)]
});

優勢：
  - 單一約束完成多步計算
  - 減少行數，提升效率
  - 可針對特定計算模式優化

複製約束（Copy Constraints）

排列論證

PLONKish 使用排列論證確保值一致性[1]：

問題：確保不同位置的值相等
  例如：row 0 的輸出 = row 1 的輸入

排列定義：
  σ: [0..n·k] → [0..n·k]
  σ(i) = j 表示位置 i 和 j 必須有相同值

排列論證：
  1. 構造累積多項式 Z(X)
  2. Z 從 1 開始，經過所有位置回到 1
  3. 若排列滿足，Z 的軌跡一致

多項式約束：
  Z(ω·X) · (a(X) + β·X + γ) · (b(X) + β·k₁·X + γ) · (c(X) + β·k₂·X + γ)
  = Z(X) · (a(X) + β·σ_a(X) + γ) · ...

佈線視覺化

電路佈線範例：
  計算 z = (x + y) · w

  Row | a    | b    | c    | 操作
  ----|------|------|------|------
  0   | x    | y    | t    | 加法：x + y = t
  1   | t    | w    | z    | 乘法：t · w = z
       ↑
       └── 複製約束：row0.c = row1.a

PLONKish 透過排列表示：
  σ(row0, col_c) = (row1, col_a)

查表論證（Lookup Arguments）

Plookup

查表是 PLONKish 的關鍵擴展[3]：

目標：證明值在預定義表格中

Plookup 協議：
  給定表格 T = {t_1, ..., t_d}
  查詢值 f = {f_1, ..., f_n}
  證明 f ⊆ T（每個 f_i 都在 T 中）

協議步驟：
  1. 排序：對 f ∪ T 排序得到 s
  2. 構造累積多項式 Z(X)
  3. 驗證 Z 的起終點及遞迴關係

效率：
  - O(n + d) 證明者時間
  - O(log(n + d)) 驗證者時間
  - 常數額外空間

ZKML 查表應用

ReLU 查表：
  T_relu = {(i, max(0, i)) : i ∈ [-2^k, 2^k]}

查詢：(input, output) ∈ T_relu

複雜度比較：
  - R1CS 位元分解：~254 約束/ReLU
  - PLONKish 查表：~1 約束/ReLU

其他常見查表：
  - Sigmoid/Tanh：預計算值
  - 範圍檢查：[0, 2^k)
  - 位元運算：XOR, AND

Halo2 查表實作

Halo2 查表配置：

// 定義查表
let table = meta.lookup_table_column();

meta.lookup("range_check", |meta| {
    let value = meta.query_advice(advice, Rotation::cur());
    let enable = meta.query_selector(s_lookup);

    vec![(enable * value, table)]
});

// 填充表格
layouter.assign_table(|| "range", |mut table| {
    for i in 0..256 {
        table.assign_cell(
            || format!("row {}", i),
            self.table,
            i,
            || Value::known(F::from(i as u64)),
        )?;
    }
    Ok(())
})?;

AIR（Algebraic Intermediate Representation）

AIR 基礎

AIR 是 STARK 使用的算術化格式[4]：

AIR 結構：
  - 執行軌跡（Execution Trace）：w × h 矩陣
  - 轉換約束（Transition Constraints）：相鄰行間的多項式關係
  - 邊界約束（Boundary Constraints）：特定位置的值約束

轉換約束範例（斐波那契）：
  a_{i+2} - a_{i+1} - a_i = 0

  Row | a
  ----|----
  0   | 1
  1   | 1
  2   | 2
  3   | 3
  4   | 5
  ...

AIR vs PLONKish

特性 AIR PLONKish
跨行存取 自然支援（轉換約束） 透過 Rotation 支援
約束形式 任意多項式 任意多項式
查表 需要額外擴展 原生 Plookup 支援
複製約束 較弱 強大的排列論證
代表系統 STARK, Cairo PLONK, Halo2

ZKML 中的應用

模型層級電路設計

全連接層 PLONKish 設計：

// y = Wx + b，其中 W ∈ F^{m×n}

配置：
  - advice columns：輸入 x、輸出 y、中間累積
  - fixed columns：權重 W、偏置 b
  - selectors：啟用 MAC 操作

約束策略：
  1. 逐元素 MAC（Multiply-Accumulate）
  2. 使用自定義門優化
  3. 批次處理多個輸出

門定義：
  s_mac · (acc_new - acc_old - w · x) = 0

卷積層設計

卷積 PLONKish 策略：

方法 1：Im2col 展開
  - 將卷積轉為矩陣乘法
  - 使用全連接層電路
  - 需要大量複製約束

方法 2：直接卷積
  - 自定義卷積門
  - 利用 Rotation 存取相鄰像素
  - 更緊湊但設計複雜

方法 3：混合策略
  - 小核直接計算
  - 大核使用 Im2col

激活函數電路

ReLU PLONKish 實作：

// 策略 1：查表（推薦）
meta.lookup("relu", |meta| {
    let input = meta.query_advice(a, Rotation::cur());
    let output = meta.query_advice(b, Rotation::cur());
    vec![
        (input, table_input),
        (output, table_output)
    ]
});

// 策略 2：分解（無查表時）
// 證明 output = input · sign
// 其中 sign ∈ {0, 1} 且 sign=1 ⟺ input≥0

GeLU / Softmax：
  - 使用多項式近似
  - 或預計算查表
  - 精度與電路大小權衡

效能優化技術

行重用（Row Reuse）

觀察：許多操作可共享行

範例：a·b + c·d = e
標準方式：2 行（2 乘法 + 1 加法）
優化：自定義門，1 行完成

meta.create_gate("double_mac", |meta| {
    let a = meta.query_advice(col_a, Rotation::cur());
    let b = meta.query_advice(col_b, Rotation::cur());
    let c = meta.query_advice(col_c, Rotation::cur());
    let d = meta.query_advice(col_d, Rotation::cur());
    let e = meta.query_advice(col_e, Rotation::cur());

    vec![s * (a*b + c*d - e)]
});

列壓縮（Column Compression）

問題：列數影響證明大小

技術：
  1. 值打包：將多個小值放入一個域元素
  2. 共享列：不同區域使用同一列
  3. 階段化：分階段填充，減少同時活躍的列

範例：位元打包
  // 8 個 bit 打包成 1 個域元素
  packed = b0 + 2·b1 + 4·b2 + ... + 128·b7

  // 使用查表驗證打包正確性

區域規劃（Region Planning）

Halo2 區域概念：

// 定義不重疊的區域
layouter.assign_region(|| "layer1", |mut region| {
    // 分配第一層
    ...
})?;

layouter.assign_region(|| "layer2", |mut region| {
    // 分配第二層
    ...
})?;

優化：
  - 最小化區域間的複製約束
  - 重用空閒行
  - 並行佈局（若可能）

複雜度分析

操作 PLONKish 行數 R1CS 約束數 備註
乘法 1 1 相同
加法 0-1 0 可合併到其他門
ReLU（查表） 1 ~254 PLONKish 大幅優勢
範圍檢查 [0, 2^k) 1 k 查表 vs 位元分解
Poseidon 雜湊 ~10 ~200 自定義門優勢
