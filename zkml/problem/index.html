問題定義與場景

ZKML 解決什麼問題？

ZKML 結合零知識證明與機器學習，解決兩大核心問題：(1) 如何在不洩露敏感資訊的前提下驗證 ML 推理的正確性；(2) 如何在保護數據隱私的同時使用 ML 服務[1]。

問題背景

AI 黑箱問題

傳統 ML 服務的信任問題：

用戶視角：
  「我無法知道服務商到底用什麼模型處理我的數據」

服務商聲稱：
  「我們使用最先進的 GPT-4 處理您的請求」

實際可能：
  - 使用便宜的小模型
  - 使用過時版本
  - 根據用戶類型使用不同模型
  - 完全偽造輸出

問題本質：
  計算過程不透明，無法驗證

數據隱私困境

ML 服務的隱私風險：

現狀：
  用戶必須提交原始數據才能使用 ML 服務

風險領域：
  - 醫療：病歷、影像、基因數據
  - 金融：交易記錄、資產資訊
  - 個人：照片、位置、通訊記錄

法規壓力：
  - GDPR：數據最小化原則
  - HIPAA：醫療數據保護
  - CCPA：消費者隱私權

需求：
  使用 ML 服務但不洩露原始數據

ZKML 問題定義

形式化定義

ZKML 系統定義：

給定：
  - 模型 M（神經網路）
  - 輸入 x
  - 輸出 y = M(x)

目標：
  生成證明 π，使驗證者確信 M(x) = y
  同時滿足特定隱私要求

隱私配置：
  public_model = true/false
  public_input = true/false
  public_output = true/false

零知識性質：
  驗證者只學到公開資訊，不學到私密資訊

核心挑戰

挑戰 描述 難度
電路規模 ML 模型轉換為巨大電路 高
非線性函數 ReLU, Softmax 電路表示困難 高
數值精度 浮點→定點轉換的精度損失 中
證明時間 大模型證明可能需數小時 高

應用場景分類

場景一：可驗證 AI 服務

場景描述：
  用戶向雲端 AI 服務請求推理，需要驗證結果正確

參與者：
  - 用戶（驗證者）
  - 服務商（證明者）

公開資訊：
  - 模型承諾
  - 輸入、輸出

證明目標：
  服務商確實使用承諾的模型進行推理

應用：
  - ChatGPT 類服務驗證
  - 醫療 AI 診斷驗證
  - 自動駕駛決策驗證

場景二：隱私 ML 推理

場景描述：
  用戶想使用 ML 服務但不洩露數據

參與者：
  - 用戶（數據持有者）
  - 服務商（模型持有者）

公開資訊：
  - 模型（或承諾）
  - 輸出（或承諾）

隱藏資訊：
  - 用戶輸入數據

應用：
  - 隱私醫療診斷
  - 隱私信用評估
  - 隱私人臉識別

場景三：區塊鏈 AI 整合

場景描述：
  智能合約需要調用 ML 模型做決策

參與者：
  - 智能合約（驗證者）
  - 鏈下執行者（證明者）

公開資訊：
  - 模型承諾（合約儲存）
  - 輸入、輸出

證明目標：
  鏈下計算符合鏈上規則

應用：
  - DAO 自動治理
  - DeFi 風險評估
  - 鏈上遊戲 AI

場景四：模型 IP 保護

場景描述：
  服務商想提供 ML 服務但保護模型智慧財產

參與者：
  - 用戶（想驗證模型能力）
  - 服務商（想保護模型）

公開資訊：
  - 模型能力承諾
  - 測試結果

隱藏資訊：
  - 模型權重

證明目標：
  模型確實具備聲稱的能力

應用：
  - MLaaS 訂閱驗證
  - 模型市場品質保證

問題空間

技術維度

ZKML 設計空間：

1. 證明系統選擇
   - SNARK (Groth16, PLONK, Halo2)
   - STARK
   - Hybrid

2. 算術化方法
   - R1CS
   - PLONKish

3. 量化策略
   - 位寬選擇
   - 縮放因子

4. 非線性處理
   - 位元分解
   - 查表
   - 多項式近似

效能-精度權衡

權衡曲線：

精度高 ────────────── 精度低
   │                     │
效能低                  效能高

配置選項影響：
  - 更高 scale → 更高精度 → 更大電路
  - 更大查表 → 更高精度 → 更多記憶體
  - 更多 bits → 更高精度 → 更慢證明

評估指標

指標 描述 目標
準確度 量化後與原始模型的差異 <1% 精度損失
證明時間 生成證明所需時間 分鐘級（理想）
驗證時間 驗證證明所需時間 毫秒級
證明大小 證明的儲存/傳輸大小 <100 KB
記憶體用量 證明過程的峰值記憶體 可接受範圍
