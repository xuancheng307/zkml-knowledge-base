配置空間與調參

論文章節對應

本頁對應論文 §5「Auto-Tuning Framework」及 RQ2「自動調優」

概述

ZKML 系統的效能高度依賴配置參數的選擇。不同於傳統機器學習僅需考慮模型準確度， ZKML 必須在準確度、證明時間、記憶體消耗 與證明大小之間取得平衡[1]。 這些參數構成一個高維度、混合型別的配置空間，手動調參既耗時又難以達到最優。

ZKML 配置參數

ZKML 系統的配置空間包含多種類型的參數，可分為量化參數與電路參數兩大類：

量化參數

參數 類型 說明 典型範圍
bit_width 整數 量化位元寬度，影響精度與約束數量 4, 6, 8, 16 bit
scale_mode 類別 量化粒度：per-tensor 或 per-channel {per-tensor, per-channel}
calibration_method 類別 校準方法：MinMax, Percentile, MSE {minmax, percentile, mse}
percentile 連續 Percentile 校準的百分位值 [99.0, 99.999]

電路參數

參數 類型 說明 典型範圍
logrows 整數 電路行數 = 2logrows，決定電路大小 12 - 24
lookup_bits 整數 查表精度，影響非線性運算準確度 8 - 16
num_inner_cols 整數 內部列數，影響 layout 效率 1 - 8
tolerance 連續 輸出容差，允許的數值誤差範圍 [0, 0.1]

參數相依性

ZKML 配置空間具有樹狀結構特性：某些參數僅在特定條件下有意義[2]。例如：

  • percentile 參數僅當 calibration_method = percentile 時有效
  • lookup_bits 必須小於或等於 logrows
  • per-channel 量化會增加額外的 scale 參數，影響電路大小
約束條件

配置參數間存在硬性約束。若 logrows 設定過小，電路可能無法容納模型； 若設定過大，則證明時間與記憶體消耗將指數級增長。

調參黑箱問題

現有 ZKML 系統面臨嚴重的調參黑箱問題：

  1. 缺乏統一評估標準：不同應用場景對準確度、速度、記憶體的權重不同
  2. 手動試錯：開發者憑經驗選擇參數，若 prove 過程耗盡記憶體或時間過久才手動調整
  3. 評估代價高昂：每次完整的 prove 操作可能需要數分鐘至數小時
  4. 配置空間龐大：混合型別參數組合數量爆炸性增長

以一個典型的 CNN 模型為例，配置空間可能包含：

  • 3 種 bit_width 選項
  • 2 種 scale_mode
  • 3 種 calibration_method
  • 13 個 logrows 值 (12-24)
  • 9 個 lookup_bits 值 (8-16)

僅這些主要參數就產生 3 × 2 × 3 × 13 × 9 = 2,106 種組合。若每次評估需要 10 分鐘， 窮舉搜索需要約 350 小時。

自動調優方法

Sequential Model-Based Optimization (SMBO)

SMBO 是一類基於代理模型的序列優化演算法[2]。 其核心思想是建構目標函數的代理模型 (surrogate model)，透過優化代理模型而非直接評估昂貴的目標函數來選擇下一個評估點。

演算法流程：


def SMBO(f, M0, T, acquisition_fn):
    """Sequential Model-Based Optimization

    Args:
        f: 目標函數 (昂貴)
        M0: 初始代理模型
        T: 最大迭代次數
        acquisition_fn: 獲取函數 (如 Expected Improvement)
    """
    H = []  # 歷史觀測

    for t in range(1, T + 1):
        # 1. 優化獲取函數找下一個評估點
        x_star = argmin(acquisition_fn(x, M[t-1]))

        # 2. 評估目標函數 (昂貴步驟)
        y_star = f(x_star)

        # 3. 更新歷史
        H.append((x_star, y_star))

        # 4. 更新代理模型
        M[t] = fit_model(H)

    return H

Tree-structured Parzen Estimator (TPE)

TPE 是專為高維度、小樣本場景設計的貝葉斯優化演算法[2]。 與傳統高斯過程 (GP) 不同，TPE 建模 $p(x|y)$ 而非 $p(y|x)$：

$$p(x|y) = \begin{cases} \ell(x) & \text{if } y < y^* \\ g(x) & \text{if } y \geq y^* \end{cases}$$

其中：

  • $\ell(x)$：由表現良好的配置形成的密度估計
  • $g(x)$：由表現較差的配置形成的密度估計
  • $y^*$：觀測值的某個分位數（通常取 $\gamma = 0.15$）

TPE 的 Expected Improvement 可簡化為：

$$\text{EI}_{y^*}(x) \propto \left(\gamma + \frac{g(x)}{\ell(x)}(1-\gamma)\right)^{-1}$$

這意味著我們應選擇在 $\ell(x)$ 下機率高而在 $g(x)$ 下機率低的配置—— 即類似於已知表現良好的配置，但不同於表現差的配置。

TPE 對 ZKML 的優勢

  • 支援樹狀配置空間：自然處理條件參數
  • 計算效率高：每次迭代複雜度為 $O(|H|)$，而非 GP 的 $O(|H|^3)$
  • 適應混合型別：可處理連續、離散、類別變數

Hyperband：基於 Bandit 的早停策略

Hyperband[3] 採用與貝葉斯優化正交的策略： 透過自適應資源分配與早停來加速隨機搜索。

核心思想是將超參數優化視為純探索的無限臂 Bandit 問題：

  • 每個配置是一個「臂」(arm)
  • 資源（如訓練迭代次數）是「預算」
  • 透過逐步增加資源並淘汰表現差的配置來高效搜索

Successive Halving

Hyperband 的核心子程序是 Successive Halving：

  1. 均勻分配預算 $B$ 給 $n$ 個配置
  2. 評估所有配置的表現
  3. 淘汰表現最差的一半
  4. 重複直到剩下一個配置

輪次 i s=4 (n,r) s=3 (n,r) s=2 (n,r) s=1 (n,r) s=0 (n,r)
0 (81, 1) (27, 3) (9, 9) (6, 27) (5, 81)
1 (27, 3) (9, 9) (3, 27) (2, 81) -
2 (9, 9) (3, 27) (1, 81) - -
3 (3, 27) (1, 81) - - -
4 (1, 81) - - - -

n = 配置數量，r = 分配資源。不同的 s 值代表不同的 探索-利用權衡：高 s 更激進（多配置少資源），低 s 更保守。

Hyperband 對 ZKML 的應用

在 ZKML 中，可將以下作為資源使用：

  • 校準資料量：使用部分資料進行量化校準
  • 簡化電路評估：先用小型子圖評估配置可行性
  • mock prove：快速檢查電路約束是否滿足

多目標優化

ZKML 調參本質上是多目標優化問題，需同時考慮多個可能衝突的目標：

  • 最小化：證明時間、記憶體使用、證明大小
  • 最大化：模型準確度

Pareto 前沿

當目標相互衝突時，不存在單一最優解。取而代之的是 Pareto 前沿—— 所有無法在不犧牲某一目標的前提下改善其他目標的解集合[4]。

定義：配置 $x$ Pareto 支配 配置 $x'$ 若且唯若：

$$\forall i: f_i(x) \leq f_i(x') \quad \text{and} \quad \exists j: f_j(x) < f_j(x')$$

加權成本函數

實務上常將多目標轉換為單一加權目標：

$$C = \alpha \cdot T_{\text{prove}} + \beta \cdot M_{\text{RAM}} + \gamma \cdot S_{\text{proof}} + \delta \cdot (1 - \text{Accuracy})$$

其中權重 $\alpha, \beta, \gamma, \delta$ 反映應用需求：

  • 鏈上驗證：高 $\gamma$（關注證明大小與 gas 成本）
  • 即時推理：高 $\alpha$（關注證明速度）
  • 資源受限環境：高 $\beta$（關注記憶體）

實務建議

參數優先順序

根據經驗，建議按以下順序調整參數[1]：

  1. logrows：首先確保電路能容納模型（過小會失敗）
  2. bit_width：在滿足準確度要求的前提下盡量降低
  3. lookup_bits：調整非線性運算的精度
  4. scale_mode：per-channel 通常更準確但電路更大
  5. calibration_method：微調量化品質

快速可行性檢查

在進行完整 prove 前，可透過以下方式快速篩選配置：

  1. Mock prove：檢查約束是否滿足
  2. 記憶體預估：根據 logrows 估算記憶體需求
  3. 準確度測試：在校準資料集上評估量化誤差

def quick_feasibility_check(config, model, calibration_data):
    """快速可行性檢查

    Returns:
        (feasible, estimated_cost) 或 (False, failure_reason)
    """
    # 1. 檢查 logrows 是否足夠
    min_rows = estimate_min_rows(model, config['bit_width'])
    if 2 ** config['logrows'] < min_rows:
        return False, "logrows too small"

    # 2. 檢查記憶體
    estimated_mem = estimate_memory(config['logrows'])
    if estimated_mem > available_memory:
        return False, "memory exceeded"

    # 3. 檢查準確度
    quant_model = quantize(model, config)
    accuracy = evaluate(quant_model, calibration_data)
    if accuracy < min_accuracy_threshold:
        return False, f"accuracy {accuracy} below threshold"

    # 4. Mock prove
    try:
        mock_prove(quant_model, config)
    except ConstraintError as e:
        return False, f"constraint failed: {e}"

    return True, estimate_cost(config)
