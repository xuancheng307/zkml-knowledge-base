查表優化

核心概念

查表（Lookup Table）是 ZKML 中處理非線性函數最有效的技術。透過預計算函數值並使用密碼學查表論證，可將 ReLU 等激活函數的約束數量從 \(O(b)\)（其中 \(b\) 為值的位元寬度）降至 \(O(1)\)[1]。

註：若不做量化且對完整域元素做位元分解，最壞情況下 \(b \approx \log|F|\)（如 254-bit）；但 ZKML 透過量化將值壓縮至 8~16 bit，使 \(b \ll \log|F|\)。

為什麼需要查表

非線性函數的挑戰

ZK 電路中，只有加法和乘法是「原生」操作[2]：

原生操作（低成本）：
  - 加法：z = x + y（無乘法門，可合併至線性組合）
  - 乘法：z = x · y（1 乘法門約束）

非線性操作（傳統位元分解方法的成本）：
  - 比較：x > y → O(b) 約束（b = 值的 bit-width）
  - ReLU：max(0, x) → O(b) 約束
  - Sigmoid：1/(1+e^{-x}) → 數百約束
  - 除法：z = x/y → O(b) 約束

典型場景（若對完整域元素做位元分解）：
  BN254 曲線，254-bit 域 → 單個 ReLU = ~254 個布林約束
  神經網路可能有數百萬個 ReLU

（註：實務上 ZKML 透過量化將輸入壓縮至 8~16 bit，
 再以查表處理 ReLU，避免 254-bit 位元分解開銷）

查表的優勢

查表方法：
  預計算表格 T = {(x, f(x)) : x ∈ domain}
  證明 (input, output) ∈ T

成本分析：
  - 表格大小：|domain|
  - 每次查表：O(1) 約束（攤銷後）
  - 總成本：O(n + |T|)，其中 n 是查詢數

ReLU 範例（8-bit 輸入）：
  傳統：254 約束 × n 個 ReLU
  查表：O(1) 約束/ReLU + 256 行表格

  若 n = 10,000 個 ReLU：
    傳統：2,540,000 約束
    查表：~10,256 約束（~250x 改進）

Plookup 協議

基本原理

Plookup 是最常用的查表協議[3]：

問題定義：
  給定表格 T = {t_1, ..., t_d}（已承諾）
  給定查詢 f = {f_1, ..., f_n}（見證的一部分）
  證明：∀i, f_i ∈ T

核心思想：
  1. 若 f ⊆ T，則 f ∪ T 排序後相鄰元素來自同一組
  2. 使用多項式編碼排序關係
  3. 驗證排序的一致性

協議細節

Plookup 步驟：

1. 排序與去重
   s = sort(f ∪ T)
   h₁, h₂ 為 s 的交錯拆分（interleaved decomposition）
   // 相同元素連續出現，透過 h₁(ωⁱ) = h₂(ωⁱ) 或 h₁(ωⁱ) = h₁(ωⁱ⁺¹) 保證相鄰性

2. 構造累積多項式（簡化形式）
   Z(X) 滿足：
   Z(ω⁰) = 1
   Z(ωⁱ⁺¹)/Z(ωⁱ) = [(1+β)·(γ + fᵢ)·(γ(1+β) + tᵢ + β·tᵢ₊₁)]
                  / [(γ(1+β) + h₁ᵢ + β·h₁ᵢ₊₁)·(γ(1+β) + h₂ᵢ + β·h₂ᵢ₊₁)]

   （完整協議請參見原論文 [3] 的 Protocol 2）

3. 驗證
   - 檢查 Z(ω⁰) = 1
   - 檢查 Z(ωⁿ) = 1（累積乘積回到起點）
   - 檢查遞迴關係在所有 evaluation points 成立

多欄查表

單欄 vs 多欄：

單欄：
  T = {0, 1, 2, ..., 255}
  用途：範圍檢查

多欄：
  T = {(x, y) : y = f(x)}
  用途：函數求值

多欄處理：
  方法 1：打包
    T' = {x + y·R : (x,y) ∈ T}，R 足夠大
    缺點：R 需要很大，可能溢出

  方法 2：隨機線性組合
    查詢 (f_1, f_2) ∈ T
    → 查詢 f_1 + θ·f_2 ∈ T'
    其中 T' = {t_1 + θ·t_2 : (t_1, t_2) ∈ T}
    θ 由 Fiat-Shamir 產生

ZKML 中的查表應用

激活函數

ReLU 查表：

表格定義（8-bit 量化）：
  T_relu = {(i, max(0, i)) : i ∈ [-128, 127]}
  大小：256 行

Halo2 實作：
  meta.lookup("relu", |meta| {
      let input = meta.query_advice(a, Rotation::cur());
      let output = meta.query_advice(b, Rotation::cur());
      let sel = meta.query_selector(s_relu);

      vec![
          (sel.clone() * input, table_input),
          (sel * output, table_output)
      ]
  });

EZKL 配置：
  lookup_range: 16      # 輸入位寬
  lookup_bits: 12       # 查表分段位寬
  logrows: 17           # 2^17 行

其他非線性函數

Sigmoid：
  T_sig = {(i, σ(i/s)) : i ∈ [-2^k, 2^k-1]}
  其中 s 是縮放因子

  精度考量：
    - 輸入範圍影響表格大小
    - 輸出需要定點數表示
    - 飽和區可合併

GELU：
  T_gelu = {(i, GELU(i/s))}
  類似 Sigmoid 處理

Softmax（部分）：
  T_exp = {(i, exp(i/s))}
  分母需要額外累加電路

LayerNorm：
  T_rsqrt = {(i, 1/√i)}
  用於歸一化分母

範圍檢查

目的：確保值在有效範圍內

應用場景：
  - 量化值邊界檢查
  - 防止溢出
  - 輸入驗證

範例（8-bit 無符號）：
  T_range = {0, 1, 2, ..., 255}

  查詢：x ∈ T_range
  證明：0 ≤ x < 256

位元分解替代方案：
  傳統：x = Σ b_i · 2^i，每個 b_i ∈ {0,1}
  需要 8 個布林約束

  查表：單次查表，O(1) 約束

表格設計考量

表格大小 vs 精度

權衡關係：

小表格（如 2^8 = 256 行）：
  優點：證明時間短，記憶體低
  缺點：輸入範圍受限，可能需要縮放

大表格（如 2^16 = 65536 行）：
  優點：更大輸入範圍，更高精度
  缺點：更多 FFT 計算，更大記憶體

最佳實踐：
  1. 分析實際值分布
  2. 選擇覆蓋 99.9% 情況的範圍
  3. 對極端值特殊處理

分段查表

問題：輸入位寬過大（如 16-bit）

分段策略：
  將 16-bit 輸入分為兩個 8-bit 查表

  x = x_high · 256 + x_low

  表格 1：T_high = {(i, f_high(i))}
  表格 2：T_low = {(i, f_low(i))}

  結果組合：
    f(x) ≈ T_high[x_high] + correction(x_low)

適用函數：
  - 可加性分解的函數
  - 分段線性近似
  - 對數/指數函數

共享表格

優化：多個電路區域共用同一表格

範例：
  所有 ReLU 層使用同一 T_relu
  所有範圍檢查使用同一 T_range

Halo2 實作：
  // 定義全局表格
  let relu_table = ReLUTable::new(&meta);

  // 多個區域引用同一表格
  layer1_config.enable_relu(relu_table.clone());
  layer2_config.enable_relu(relu_table.clone());

節省：
  - 表格只需承諾一次
  - 設置開銷不重複

進階技術

動態表格

問題：某些函數依賴運行時參數

範例：Softmax 的溫度參數
  softmax(x/T) 中的 T 可變

解決方案：

方法 1：多版本表格
  T_softmax_T1, T_softmax_T2, ...
  運行時選擇

方法 2：插值
  預計算少量點
  使用多項式插值

方法 3：參數化查表
  T = {(x, T, f(x, T))}
  三欄查表

tlookup（張量查表）

定位說明

tlookup 不是通用 lookup argument（如 Plookup / Caulk），而是 zkLLM 針對特定張量結構提出的應用層優化。它利用張量可分解為外積的特性減少查表次數，僅適用於滿足此結構假設的場景。

zkLLM 引入的張量查表技術，專為 LLM 中的大規模矩陣查表設計[4]：

比較基線說明

下方比較的「標準方法」指的是向量化成員證明（vectorized membership proof），即對 Q 個查詢分別生成成員證明後批次驗證。這與 PLONKish 聚合式 lookup（如 Plookup / Halo2 lookup）不同——後者將所有查詢聚合為單一多項式關係，Prover 成本為 O((Q + |T|) log(Q + |T|))，Verifier 成本則取決於承諾方案（KZG 為 O(1) 配對，IPA 為 O(n) MSM）。

問題：矩陣運算產生大量查詢

向量化成員證明（vectorized membership proof）：
  n×m 矩陣 → Q = n·m 次查表
  Prover 成本：O(Q · log Q) 用於排序/證明生成
  Verifier 成本：O(Q) 群運算（逐查詢驗證）
  （註：此為 zkLLM 論文中比較的基線設定）

tlookup 優化（zkLLM §5.2）：
  將 n×m 張量 V 分解為外積 V = u ⊗ v
  其中 u ∈ F^n, v ∈ F^m
  只需證明 u_i ∈ T 且 v_j ∈ T
  → Prover 成本降為 O((n + m) · log(n + m))
  → Verifier 成本降為 O(n + m)

限制條件：
  - 僅適用於可表示為外積的張量
  - 實務上用於 softmax 輸出等特定結構

適用場景：
  - Attention softmax 輸出驗證
  - 批次激活函數（若可分解）
  - 具有 Kronecker 結構的權重矩陣

Caulk / Caulk+

Caulk 系列協議專為超大表格優化[5][6]：

Caulk (CCS 2022) 特點：
  - 預處理模型：O(|T| log |T|) 預處理，之後查詢獨立於表大小
  - 驗證時間：O(log |T|)
  - 假設：需 structured reference string (SRS)
  - 證明大小：O(1) 群元素

Caulk+ (ePrint 2022) 改進：
  - 驗證時間：O(1)（配對運算數固定）
  - 更小證明大小
  - 相同預處理模型

適用場景：
  - 百萬行以上的靜態表格
  - 稀疏查詢模式（查詢數 ≪ 表大小）
  - 多次使用同一表格

注意事項：
  - 需要 KZG 承諾與可信設置
  - 預處理成本較高，適合表格長期不變的場景

實作考量

記憶體管理

表格儲存：
  - 表格在 Setup 階段承諾
  - 證明過程中需要完整表格

優化策略：
  1. 表格壓縮（若有規律）
  2. 按需載入（分頁）
  3. GPU 記憶體利用

範例：
  2^20 行表格，每行 64 bytes
  = 64 MB 記憶體

  對於多個表格：
    總記憶體 = Σ |T_i| × row_size

並行化

查表的並行機會：

1. 多表並行
   不同表格的查表可並行處理

2. 批次查詢
   同一表格的多個查詢可批次處理

3. GPU 加速
   排序和累積多項式計算可 GPU 化

效能提升：
  單核：100 ms / 1000 查詢
  多核：20 ms / 1000 查詢（5x）
  GPU：5 ms / 1000 查詢（20x）
