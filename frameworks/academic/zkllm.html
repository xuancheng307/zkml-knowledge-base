zkLLM

核心概念

zkLLM 是首個實現十億參數級大型語言模型（LLM）可驗證推理的零知識證明系統，由加拿大滑鐵盧大學（University of Waterloo）的 Haochen Sun、Jason Li 與 Hongyang Zhang 開發[1]。透過創新的 tlookup 和 zkAttn 技術，zkLLM 相較於先前方法實現約 50 倍加速，將 13B 參數模型的證明時間降至 15 分鐘內。

研究背景

LLM 驗證挑戰

大型語言模型驗證面臨獨特挑戰[1]：

挑戰 描述 規模
模型大小 參數數量極大 7B-175B 參數
計算密度 矩陣乘法數量巨大 每個 token 數萬億 FLOPs
非線性操作 Softmax、LayerNorm 每層數千次
Attention 機制 序列長度平方複雜度 O(n²) attention 分數

現有方法的限制

傳統 ZKML 方法在 LLM 上的問題：

EZKL/Halo2：
  - 13B 模型電路太大，無法載入記憶體
  - 證明時間估計：數百年

ZKML (EuroSys 2024)：
  - 針對 CNN 優化
  - Softmax 電路複雜度過高
  - 不支援 Transformer 結構

zkVM (RISC Zero 等)：
  - 通用但效率低
  - LLM 推理時間過長

核心技術

tlookup：張量查表

tlookup 是 zkLLM 的核心創新，擴展查表論證到高維張量[1]：

傳統 lookup vs tlookup：

傳統 Plookup：
  證明 f ⊆ T，其中 f, T 是向量
  複雜度：O(|f| + |T|)

tlookup 擴展：
  證明 F ⊆ T，其中 F 是張量，T 是表格
  關鍵優化：利用張量結構減少複雜度

張量分解：
  F ∈ F^{n×m} 可分解為：
  F[i,j] = lookup(row_index=i, col_index=j)

複雜度：O(n·m) → O(n + m)（在特定情況下）

tlookup 協議

tlookup 證明結構：

Setup：
  1. 預計算查表 T（函數值域）
  2. 建立多項式承諾結構

Prove：
  1. 對張量 F 進行行列分解
  2. 證明每行/列的查表關係
  3. 使用隨機線性組合壓縮

Verify：
  1. 驗證分解一致性
  2. 驗證查表證明
  3. 常數次配對運算

複雜度改進：
  傳統：O(n·m) 承諾 + O(n·m) 查表
  tlookup：O(n + m) 承諾 + O(n + m) 查表

zkAttn：零知識注意力

zkAttn 針對 Transformer 的 Attention 機制設計[1]：

標準 Attention：
  Attention(Q, K, V) = softmax(QK^T / √d_k) · V

zkAttn 分解：
  1. 矩陣乘法 QK^T：使用 tlookup 優化
  2. Scaling：線性操作，低成本
  3. Softmax：最困難的部分

Softmax 處理：
  softmax(x)_i = exp(x_i) / Σ_j exp(x_j)

  策略 1：多項式近似
    exp(x) ≈ 1 + x + x²/2 + ...
    精度有限，不適合長序列

  策略 2：分段線性近似 + 查表
    將輸入範圍分段
    每段使用查表

  策略 3：zkLLM 方法
    使用 tlookup 直接查表 exp 值
    利用 Attention 結構簡化 Σ 計算

zkAttn 協議細節

zkAttn 協議：

輸入：Q, K, V ∈ F^{n×d}

步驟 1：計算 S = QK^T
  使用 tlookup 證明矩陣乘法
  複雜度：O(n + d) 而非 O(n²·d)

步驟 2：計算 exp(S / √d)
  使用 tlookup 對每個元素查表
  預計算：T_exp = {(i, exp(i/√d)) : i ∈ range}

步驟 3：計算 Softmax 分母
  D_i = Σ_j exp(S_{ij} / √d)
  使用累加電路，O(n²) 加法

步驟 4：計算輸出
  O = softmax(S) · V
  利用線性關係簡化

總複雜度：O(n² + n·d) 而非 O(n²·d)

系統架構

編譯流程

zkLLM 編譯流程：

輸入：PyTorch/Hugging Face 模型

1. 模型解析
   - 提取 Transformer 層結構
   - 識別 Attention、FFN、LayerNorm

2. 電路生成
   - 每層生成獨立電路
   - 使用 zkAttn 處理 Attention
   - 使用 tlookup 處理非線性

3. 證明分割
   - 將長序列分割為區塊
   - 並行證明各區塊
   - 累積最終證明

4. 優化
   - 權重預處理
   - 查表預計算
   - 記憶體優化

記憶體管理

LLM 記憶體挑戰：

問題：
  13B 模型權重：~26 GB (FP16)
  電路表示：數百 GB
  證明過程：TB 級中間數據

zkLLM 解決方案：

1. 分層處理
   - 一次只處理一層
   - 層間傳遞激活值承諾

2. 流式證明
   - 不需要完整電路在記憶體
   - 邊計算邊證明

3. 增量承諾
   - 權重預承諾（離線）
   - 運行時只處理激活值

記憶體使用：~50 GB（可在消費級 GPU 上運行）

與其他方法比較

13B LLM 證明時間比較：

傳統 SNARK（電路編譯）：
  - 預估：~100,000 年
  - 原因：O(n³) 電路大小

EZKL + Halo2：
  - 預估：~1,000 年
  - 原因：Softmax 電路過大

zkVM (RISC Zero)：
  - 預估：~10 年
  - 原因：通用執行開銷

zkLLM：
  - 實測：<15 分鐘
  - 改進：約 50 倍（相較先前最佳方法）
  - 支援模型規模擴大 10 倍

技術限制

精度考量

量化需求：

zkLLM 使用定點數表示：
  - 權重：INT8
  - 激活值：INT16
  - 累積器：INT32

精度影響：
  - 困惑度（Perplexity）略有上升
  - 在大多數任務上可接受
  - 某些精細任務可能受影響

與 FP16 推理比較：
  模型        | FP16 PPL | zkLLM PPL | 差異
  ------------|----------|-----------|------
  LLaMA-7B    | 5.68     | 5.85      | +3%
  LLaMA-13B   | 5.09     | 5.23      | +2.7%

序列長度限制

Attention 複雜度：O(n²)

限制因素：
  - 查表大小隨 n² 增長
  - 記憶體需求增加
  - 證明時間增加

當前支援：
  - 標準：2048 tokens
  - 擴展：4096 tokens（需更多資源）

長序列策略：
  1. 分塊處理（可能影響品質）
  2. 滑動窗口 Attention
  3. 稀疏 Attention 變體

應用場景

可驗證 AI 服務

場景：用戶驗證 AI 服務商確實使用聲稱的模型

流程：
  1. 服務商公開模型承諾
  2. 用戶提交請求
  3. 服務商生成回覆 + zkLLM 證明
  4. 用戶驗證證明

優勢：
  - 防止服務商使用較弱模型
  - 保護模型權重隱私
  - 用戶無需信任服務商

區塊鏈 AI 代理

場景：智能合約呼叫 LLM 做決策

流程：
  1. 合約定義 LLM 決策邏輯
  2. 鏈下執行 LLM 推理
  3. 提交 zkLLM 證明到鏈上
  4. 合約驗證並執行

應用：
  - DAO 治理決策
  - 自動交易策略
  - 內容審核
