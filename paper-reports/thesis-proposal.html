1. 出發點：ZKML 的 Optimizer 做了什麼

本研究以 EuroSys 2024 的 ZKML 當起點，因為它把 zkML 的核心問題講得很清楚：

核心問題：同一個 ML 模型要變成 ZK proof，不能暴力試所有電路排法（太貴），所以需要 compiler + optimizer。

ZKML 的「內層 Optimizer」做這些事：

  1. 把模型轉成 logical plans（每層可能有不同 gadget/實作選項）
  2. 再轉成 physical plans：決定電路 layout（columns/rows 的分配、怎麼 pack constraints）
  3. 用 cost estimation（主要看 FFT/MSM/lookup 等成本）去挑「最省成本」的 plan
  4. 掃 columns 的不同配置，再找最適合的 rows = 2^k（k 的選擇影響巨大）
  5. 為避免組合爆炸，用 heuristic 把空間砍小（例如同一 configuration 內限制層級選擇一致）

重要觀察

ZKML 的 optimizer 本質是：在固定電路表達/固定框架前提下，做 layout/gadget 層級的 cost-guided search。

logrows (=k) 其實在 ZKML 內層就已經是核心要處理的變數之一，所以如果論文只說「要調 logrows」會非常弱，也很像重做。

2. 研究缺口（Gap）

ZKML 解得很好的是「電路內部怎麼排比較便宜」，但值得往上做的缺口是：

Gap A
端到端配置是黑箱
Gap B
選參數常是試錯
Gap C
跨 Stack 無法直接調

缺口 A：端到端 Configuration 仍是黑箱

在真實使用場景裡，大家最常卡住的是：

  • 量化/定點表示到底怎麼設（bit-width、scale factor、rounding、per-channel...）
  • lookup table 的精度/範圍怎麼選（精度高表就大，表大又會逼 k 跳階）
  • 非線性（exp/softmax/div）用哪種近似或 gadget 方案
  • 電路資源（columns budget、lookup strategy）怎麼配
  • 甚至 PCS（KZG/IPA）不同，最佳配置的形狀可能不同

這些不是單純靠 ZKML 的 layout optimizer 就能解完的，因為它的主要搜尋維度在電路排版與 gadget/layout 的組合，而不是把「量化＋近似＋lookup 設計」當成全局的主搜尋維度。

缺口 B：現在選參數常常是「工程試錯」

就算某些工具會給「建議值」，也不代表是最省 proving cost 的；而且不同模型、不同硬體、不同 PCS/stack 下，建議值可能完全不適用。

領域真正需要的是：一個更上層的 Auto-Tuning 方法論，把「配置空間」系統化、把結果變成 Pareto frontier 與可解釋規則。

缺口 C：ZKTorch 的參數/架構不同

ZKTorch 走的是「拆成 basic blocks + accumulation」的 proving stack，跟「整個模型編成一張 halo2 大電路」不是同一種抽象。

所以 ZKML 內層 optimizer 本來就不可能去調 ZKTorch 那一套 stack 的參數（例如 block 選擇、累積策略、平行度配置等）。

2.5 研究問題（Research Questions）

基於上述研究缺口，本研究提出以下四個核心研究問題：

RQ1：量化–成本關係

不同量化與證明配置如何影響：

  1. 模型精度（Top-1 accuracy、calibration metrics 如 ECE/AURC）
  2. ZK 成本（約束數、prover time、peak RAM、proof size、on-chain gas）

→ 建立 configuration 到 metrics 的定量映射

RQ2：自動調優

能否設計 Auto-Tuning 演算法，在給定：

  • 模型 f、資料集 D
  • 精度門檻（如 Top-1 drop ≤ 1%）
  • 有限試驗預算（如 50-100 次）

條件下，自動搜尋 Pareto 最佳配置？

→ 本研究的核心技術貢獻

RQ3：跨模型泛化

對不同架構（MLP / CNN / Transformer），最佳設定是否呈現一致 pattern？

能否總結成「ZK-friendly 配置準則」？

→ 從實驗結果萃取可重用的設計規則

RQ4：安全性與健全性

激進量化下是否仍能保持 ZK 證明的正確性（correctness）與健全性（soundness）？

是否有 overflow/wrap-around 破壞語義正確性的情況？

→ 確保配置選擇不會違反密碼學安全性

3. 核心主張：外層 Tuner / Meta-optimizer

論文核心主張

沿用 ZKML 的基本精神：用成本模型/統計量引導搜尋，而不是暴力 profiling。
但把最佳化層級往上拉：做一個外層 tuner（meta-optimizer），
去搜尋「端到端 configuration」，把內層的 ZKML optimizer 當作 subroutine。

內層（ZKML Optimizer）

給定某種表達與設計，幫我把電路排到最好

  • Layout 選擇
  • Gadget 組合
  • FindOptimalK

外層（本研究的 Tuner）

決定「到底用哪種量化/lookup/近似策略」才值得

  • 量化策略
  • Lookup 設計
  • 資源配置
  • Stack 選擇

最終輸出

不是一個「我覺得不錯的參數」，而是：

  1. Pareto 最佳配置集合（在 accuracy 門檻下）
  2. 可解釋的調參規則

4. 參數空間：分層＋條件式定義

本研究不會把論文綁死在 bit/scale/k/lookup 這四個。更完整、更像研究的做法是把參數分層，並且允許條件式參數（tree-structured search space）：

Layer 1 量化/算術化（Arithmetization / Quantization）

直接影響精度與溢位風險，也影響 lookup domain 與電路成本：

  • bit-width（可做 per-layer / mixed precision）
  • scale factor（SF）策略：per-tensor / per-channel / per-layer
  • rounding mode：nearest / floor（甚至可研究 stochastic rounding）
  • clipping/saturation（要不要截斷、截斷界怎麼設）
  • calibration 設定：用多少校準資料估 range（max vs percentile）

Layer 2 非線性與 Lookup 近似策略

這是 zkML 成本炸裂的核心區：

  • lookup precision（粒度/精度）
  • lookup input range（例如 exp 的 clip range，softmax 的穩定化策略）
  • table sharing（多算子共用表 vs 分開）
  • piecewise table（分段近似 vs 單表）
  • 某些算子選 lookup 還是 bit-decomposition gadget（例如 max/ReLU）

Layer 3 電路資源/佈局（Circuit Resources）

避免把所有 layout 細節都變成搜尋維度（太爆），但保留「能影響整體成本結構」的 knob：

  • columns budget（或某些 gate/lookup column 的配置策略）
  • lookup 策略（表大小上限、表數量、每步可用 lookup 數量）
  • logrows（2^k）更傾向當成「內層推導出的最小可行 k」而不是外層主參數
    （因為它在 ZKML 本來就會被 FindOptimalK 處理；可把它變成 deterministic 內層決策）

Layer 4 PCS / Proving Backend

明確區分兩個不同層級：

  • PCS backend：KZG / IPA（同一種電路前端下，承諾方案不同，成本結構不同）
  • Proving stack：Halo2-style compile-to-circuit vs ZKTorch-style block+accumulation
    （這不是 PCS backend，是整條管線不同）

5. 研究方法：讓 Tuning「不是瞎調」

研究方法不只是「跑很多實驗歸納規則」，而是採用一個比較完整的研究套路：

5.1 形式化：帶約束的多目標最佳化

問題定義

給定模型 f、資料集 D、精度門檻 τ，尋找配置 c ∈ C 使得：

minc∈C   cost(c) = prover_time(c) + λ₁ · 1[acc(c) < τ] + λ₂ · gas(c)

符號定義

符號說明
c ∈ C配置向量，包含量化參數、lookup 設定、電路資源等
prover_time(c)在配置 c 下生成證明所需時間
acc(c)量化後模型在驗證集上的精度
τ精度門檻（如 Top-1 accuracy ≥ 原始模型 - 1%）
gas(c)鏈上驗證成本（可選目標）
λ₁, λ₂懲罰係數，控制約束違反與次要目標權重

多目標形式

實際上為 Constrained Multi-Objective Optimization：

  • 主目標：最小化 proving time、peak RAM、proof size
  • 硬約束：accuracy ≥ τ、配置必須可行（能編譯、能生成 witness、能通過 constraint check）
  • 軟約束：避免 overflow/wrap-around（可透過 penalty 處理）
  • 輸出：Pareto frontier（而不是單一最佳點）

5.2 多保真（Multi-Fidelity）評估

核心概念

Full proving 成本極高（可能需要數分鐘到數小時），無法對每個配置都執行。因此採用漸進式評估策略：用便宜的代理指標快速篩選，只對有潛力的配置執行完整證明。

每個配置 θ 的評估，分成三個層級：

層級 內容 成本 用途
F0 compile + 電路統計量（rows_needed、cols、lookups...） ~秒級 大量探索，過濾明顯不可行配置
F1 witness generation + mock/constraint check ~分鐘級 確保可行性、抓 overflow、精度評估
F2 full proving + verification ~分鐘~小時 只對 Pareto 候選做，獲得真實成本

Multi-Fidelity 評估流程

  1. F0 快速篩選：對所有候選配置執行編譯，收集電路統計量
  2. 啟發式過濾：根據 rows/cols 估計剔除明顯超出資源限制的配置
  3. F1 可行性驗證：對通過 F0 的配置生成 witness，檢查 constraint satisfaction
  4. Pareto 候選選擇：根據 F0+F1 的代理指標，選出 Pareto frontier 候選
  5. F2 精確評估：僅對候選執行 full proving，獲得真實 prover time 與 proof size

優勢：在有限 trial budget（如 100 次）下，可探索 1000+ 配置空間，同時保持最終結果的可信度。

5.3 搜尋策略：Sample-Efficient Tuner

為什麼不能暴力搜尋？

配置空間為 tree-structured（條件式參數），維度高且混合離散/連續變數。若每次 F2 評估需 10 分鐘，100 次試驗就需 16+ 小時。因此需要 sample-efficient 的搜尋策略。

工程穩定版

  • Random warm-up：初始 10-20 次隨機採樣建立先驗
  • TPE（Tree-structured Parzen Estimator）：處理條件式參數空間
  • RandomForest-BO：對離散變數友善

適合快速原型驗證

學術加分版

  • Constrained Multi-Objective BO：同時處理多目標與約束
  • Hypervolume Improvement：最大化 Pareto frontier 覆蓋
  • Feasibility Model：學習可行區域，避免浪費預算在不可行配置

適合論文發表

演算法框架（Pseudo-code）

Algorithm: Multi-Fidelity ZKML Auto-Tuner
Input: Model f, Dataset D, Budget B, Accuracy threshold τ
Output: Pareto frontier P*

1. Initialize surrogate model M, Pareto set P ← ∅
2. for t = 1 to B do
3.   c_t ← AcquisitionFunction(M, P)    // 選擇下一個配置
4.   stats ← F0_Compile(c_t)            // 快速編譯取得統計量
5.   if stats.feasible then
6.     acc, witness_ok ← F1_Witness(c_t) // 生成 witness 檢查
7.     if witness_ok AND acc ≥ τ then
8.       cost ← EstimateCost(stats)      // 用代理指標估計成本
9.       UpdateSurrogate(M, c_t, cost)
10.      if IsParetoCandidate(c_t, P) then
11.        real_cost ← F2_FullProving(c_t)  // 完整證明
12.        P ← UpdatePareto(P, c_t, real_cost)
13. return P

5.4 內層/外層（Bi-level）的關鍵點

不是重做 ZKML

「layout 找最小可行 k*、最小 rows grid、columns 掃描」這種工作放在內層（沿用 ZKML 思想/或現有 compiler），外層 tuner 只負責決定「哪種 configuration 值得用」。

研究貢獻非常清楚：做的是 meta 層的 configuration selection，不是把 ZKML 內層 optimizer 重寫一次。

5.5 可解釋規則（Rule Mining）

把跑出的 trial logs 做：

  • Sensitivity analysis（哪些參數最敏感）
  • Decision tree / rule list / SHAP（產生「如果模型是 softmax-heavy → lookup precision 要怎麼選」這種規則）

讓結果不只是跑出一條 Pareto，而是真的產生「設計準則」。

5.6 密碼學正確性分析（Cryptographic Soundness）

為什麼需要密碼學分析？

激進的量化配置可能導致 overflow/wrap-around，使得 ZK 證明的語義正確性被破壞。即使證明驗證通過，實際計算結果可能與預期不符。

ZK 關係式定義

對於量化後的 ML 推理，定義 ZK relation R：

R = { (x, y; w, θ) : y = fquant(x; w, θ) ∧ NoOverflow(x, w, θ) }

其中：

  • x：公開輸入（模型輸入）
  • y：公開輸出（推理結果）
  • w：私有 witness（量化後權重、中間計算）
  • θ：配置參數
  • fquant：量化後的模型函數

Soundness 條件

證明系統的 Soundness 要求：若 verifier 接受證明，則 statement 為真。在 ZKML 場景下：

  1. 計算正確性：電路約束正確編碼了量化後的計算
  2. 無溢位：所有中間值在有限域內不發生 wrap-around
  3. 語義一致性：ZK 證明的結果 = 原始量化模型的結果

Overflow 檢測策略

本研究在 F1 階段加入 overflow 檢測：

檢測方法說明
Range Check驗證所有中間值落在預期範圍 [−2b−1, 2b−1−1]
Constraint Satisfactionmock prover 檢查所有約束是否滿足
Statistical Sampling對多筆測試輸入執行，檢測 edge case overflow

若檢測到 overflow，該配置標記為不可行（infeasible），不進入 Pareto 候選。

安全配置的必要條件

一個配置 c 被視為「安全」需滿足：

  1. 所有 lookup 輸入值落在 table 定義範圍內
  2. 乘法累加結果不超過有限域模數的安全範圍
  3. 定點數表示的精度足以區分不同輸出
  4. constraint satisfaction rate = 100%（無約束違反）

6. 應用場景與實務價值

本研究的 Auto-Tuning 框架在以下場景具有直接的實務價值：

🔗 區塊鏈上的可驗證 AI 推論

  • 隱私 KYC / 風險評分：模型計算風險分數，僅公開結果與 ZK 證明，不洩漏敏感資訊
  • 去中心化預言機：第三方節點用私有模型生成預測，附 ZK 證明供鏈上驗證
  • ZK Rollup / L2 決策：Rollup sequencer 用 AI 做排序或風險判斷，透過 ZK 防止作弊

錯誤的 ZKML 配置（如 bit 過大導致證明時間 10 分鐘）會讓系統不可用

☁️ 雲端 ML 服務的第三方驗證

  • 根據客戶需求（Top-1 drop ≤ 0.5%、latency ≤ 5s）自動找到適合配置
  • 讓 ZKML 變成「可參數化的 trade-off」，而非黑箱開關
  • 支援 SLA-aware 的證明生成

📘 ZKML 工程師的設計指南

本研究將提供：

  • ezkl / ZKTorch 等框架的調參建議
  • 公開實驗報告：不同 bit / scale / logrows 的 cost 曲線與最佳點
  • 可重用的 ZK-friendly 配置準則

為什麼 Auto-Tuning 對這些場景很重要？

現狀是：開發者憑經驗選參數，若 prove 爆 RAM 或時間過久才手動調整，無自動化與統一評估標準。

本研究要解決的就是：讓配置選擇從「工程試錯」變成「可重現的方法論」。

7. ZKTorch 延伸

重要聲明

這裡不會說「同一組參數直接套用到 ZKTorch」，而是更嚴謹地說：

將 ZKTorch 視為另一個 proving stack。外層 tuner 會先在 Halo2-style stack 上完成方法與評估；接著做延伸實驗：同一套 tuning 方法論是否能遷移到 ZKTorch-style stack。

延伸的最小可行做法

  1. 定義統一的 metrics schema（accuracy、time、RAM、proof size...）
  2. 在 ZKTorch 內部挑一小組它的可調參數（例如 block 選擇/某些精度設定/平行度等）形成 θZKTorch
  3. 讓 tuner 把「stack」當成 categorical 選項：
    • 在某些需求（例如 proof size 很嚴格 vs proving time 很嚴格）下，tuner 是否會偏好不同 stack
  4. 評估「warm-start/transfer」：在 Halo2-stack 上學到的先驗，能否讓 ZKTorch 的搜尋更快找到好解

這樣就算 ZKTorch 在絕對速度上更強，本研究的貢獻仍然成立：

做的是「怎麼自動選擇配置與堆疊」，不是要跟 ZKTorch 拼單點速度。

8. 執行路線

用「先做可用，再做漂亮」的路線：

1

把 Runner 做到完整（最重要）

輸入 θ → 輸出 metrics（acc/cost/feasible + 電路統計 + log）

先用小模型（MLP/tiny CNN）跑通 multi-fidelity pipeline。

2

做第一版 Tuner（可跑出 Pareto）

先用 TPE/BO，跑出 Pareto frontier，並做 baseline 對照（default、random、簡單 heuristic）。

3

擴參數空間（從四個變多層）

加入 rounding/clipping、table sharing、piecewise、mixed precision 等，做 sensitivity + rule mining。

4

延伸到 ZKTorch（方法遷移/Stack Selection）

把 stack 作為 categorical 選項或做 transfer，完成「外層 tuner」的更大敘事。

一句話收尾

核心定位

本研究不是要重做 ZKML 的 optimizer，而是把它當作內層，往上做一個「端到端 configuration 的 Auto-Tuner」。

要解的問題是：在參數更多、堆疊更多（Halo2-stack / ZKTorch-stack）、而且每次 full proving 都昂貴的現實下，
