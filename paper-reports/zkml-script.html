開場

大家好，今天我想報告的主題是 ZKML——全名是「ZKML: An Optimizing System for ML Inference in Zero-Knowledge Proofs」，中文我會稱它是「零知識證明機器學習推論最佳化系統」。

我今天的講法會完全按照我這份報告頁面上的架構，一個區塊一個區塊往下走。你如果有在看投影片或網頁，也會發現順序是一樣的：研究動機、應用場景、技術背景、系統架構、Gadgets、Optimizer、實驗結果，最後是結論與限制。

核心價值：把「相信平台」改成「驗證平台」

模型提供者每次給你推論結果的同時，還會給你一個零知識證明（Zero-Knowledge Proof, ZKP），讓你可以驗證這個結果確實是由「事先承諾的模型」算出來的，而且在過程中不需要公開模型權重。

區塊一：研究動機

先從問題背景開始。現在很多機器學習模型（Machine Learning, ML）其實都部署在封閉系統（closed systems）或 API 後面。使用者拿到的只是「輸入 → 輸出」的服務，你看不到模型裡面到底怎麼做決策。

這件事不只是在學術上有趣，它實際上會影響很具體的生活與社會決策。例如：

  • 社群媒體推薦系統會影響你看到的資訊流
  • 醫療診斷 AI 會影響重大決策
  • 信用評分模型會影響貸款審批

當這些模型越來越重要，大家自然就會要求透明度（transparency）與可驗證性（verifiability）。最直覺的做法，就是把模型權重（model weights）公開，把資料公開。

核心矛盾：使用者想要透明、可驗證；企業端卻有合理顧慮，包含隱私與商業機密。

很多模型是用私密資料訓練的，你不可能要求它把訓練資料全摊開；而且模型權重本身可能是公司花極大成本訓練出來的資產，不會輕易公開。

這時候，ZKML 想解的就是：我不要你公開權重，但我也不要完全「相信你」。我希望你用零知識證明來「證明你沒騙我」。

Figure 1 說明

請大家看一下報告頁面上的 Figure 1，它用 Twitter 推薦作為例子。沒有 ZKML 的時候，平台說它用模型 M 幫你排序推薦內容，但你其實無法確認它是不是偷偷用另一個模型 M'。有了 ZKML 之後，平台除了給你「Interesting tweets？」的推薦結果，還會附上一個「ZKML proof」。你就可以驗證：這個輸出確實是由你期待的模型 M 算出來的。

ZKML 不證明什麼？它不保證模型是「好的」或「公平的」；它只保證「平台沒有在計算過程上說謊」。如果模型本身偏誤（bias）很大，ZKML 不會神奇地讓它變公平。ZKML 解的是「誠實性」與「可驗證性」，不是「價值判斷」。

區塊二：應用場景

報告頁面列了三個典型用途：無需信任的審計、隱私生物辨識、可驗證信用評分。

1. Trustless Audits（無需信任的審計）

問題是什麼？很多 ML 模型訓練在私人數據上，例如推薦系統。使用者想審計：你是不是照你說的規則運作？你是不是偷偷改模型？

ZKML 的解法是：模型提供者先 commit 到固定模型，之後每次輸出都附 ZK proof。你不用看到權重，但你可以驗證它確實用那個承諾模型產生結果。

2. Private Biometric Authentication（隱私生物辨識）

問題是：線上服務想確認你是真人，但很多生物辨識方案侵犯隱私，因為你要把臉、指紋、聲紋交給平台。

做法是結合 attested sensors——帶有硬體簽章的感測器。使用者在本地拍照或感測，感測器對資料簽章，然後本地跑人臉比對模型，最後產生 ZK proof。平台只驗證 proof，不需要拿到你的照片或生物特徵。

3. Trustless Credit Scores（可驗證信用評分）

這個很常出現在區塊鏈場景。貸方想知道借方信用如何，但借方不想把完整財務與行為資料公開。做法是用 ZK-SNARK 證明這個分數確實依照承諾的 ML 模型誠實計算。

共同特性：它們要完整安全，通常需要結合其他技術，例如 verified databases、attested sensors。ZKML 專注的是「ML inference 的可驗證性」這一環。

區塊三：技術背景

這個區塊主要要回答兩個問題：第一，ZKML 在做 proof 的流程是什麼？第二，它底層用的 halo2 電路模型，為什麼會讓「最佳化」變得很重要？

ZKML 證明與驗證流程（Figure 2）

報告頁面把它拆成三個階段：

  1. Model Compilation：把模型編譯成電路（circuit）
  2. ZKML Proving：把「輸入 + 電路」丟給 Prover，產生 Proof
  3. ZKML Verification：Verifier 用 verifying key 驗證 proof

halo2 電路表示

它把電路想成一個 2D grid，也就是二維格子表格。每個 cell 裡面是一個有限域（finite field）元素。然後，用 constraint（約束）把這些 cell 綁起來。

約束分成三類：

  • 多項式約束：要求某個多項式算出來要等於零，「你必須滿足某條等式」
  • 複製約束：要求兩個 cell 值要一樣，「這兩格必須相等」
  • 查表約束：要求某些值必須出現在預先定義的表裡，「你只能從合法表格裡選值」
關鍵限制：Rows 必須是 2k
你只要 row 數稍微超過 2k 一點點，你可能就得跳到 2(k+1)，整體成本可能接近翻倍。所以「電路布局」直接決定你證明快不快。

ReLU 範例：為什麼同一運算有多種表示法？

方法一：位元分解——把 x 展開成 bit，檢查符號位，再重組。優點是不需要 lookup table；缺點是很吃 cell，位寬 b 的話要 b+2 個 cell。

方法二：Lookup Table——直接建表存 (x, ReLU(x)) 的對應，電路內只要少量 cell 就能查表；但表大小至少 2b 行。

哪個快？不一定。如果只做一次 ReLU，做 lookup 可能反而更貴；但如果做很多次 ReLU，lookup 的攤提成本可能更划算。

同一運算，選錯實現方式，效能可能差 24 倍！

區塊四：系統架構

ZKML 五層架構（Figure 3）

  • ZK Backend：底層證明系統使用 halo2，支援 KZG 與 IPA 兩種 commitment schemes
  • Low-level Gadgets：把常用運算做成電路積木（Shape, Arithmetic, Non-linearities, Specialized）
  • Logical Layers：ML 層抽象，像 Fully connected、Conv2D 等
  • Core：Aggregator 把 layers 組成電路；Layout Optimizer 選最有效率的佈局
  • User Tools：提供 Prover、Verifier、Benchmark 等工具

ZKML 不是只有「能做電路」，它是一整個「從模型到最佳電路、再到 proof 與驗證」的系統。

KZG vs IPA

KZG Commitment：需要 Trusted Setup（PSE 已完成 228）。Proof size 較小，驗證極快（一個 pairing check）。適合很在乎驗證速度的場景。

IPA Commitment：Transparent，不需要 trusted setup。但 proof size 較大，verification 較慢。適合更在乎去中心化與透明性的場景。

Optimizer 流程（Figure 4）

四階段：ML Model Specification → Logical Plans → Physical Plans → Cost Estimation

ZKML 的核心不是只做「轉換」，而是做「轉換 + 最佳化」。

區塊五：Gadgets 設計

四大類 Gadgets

  • Shape：reshape、slice、concat，幾乎是 Free（只是重排索引）
  • Arithmetic：加減乘除、dot product，同一運算有多種電路寫法
  • Non-linear：ReLU、sigmoid、tanh，多數用 lookup table 做
  • Specialized：主要是為了 Softmax

Softmax 的突破

Softmax 是向量函數，沒辦法直接用 lookup table 表示整個向量。ZKML 用兩個策略：

第一，數值穩定技巧：先減掉最大值，softmax(xi) = softmax(xi - maxj xj)，讓 exponentials 輸入都 ≤ 0。

第二，分解成三個 gadgets：

  1. Maximum Gadget：找最大值，用多項式約束 (c-a)(c-b)=0 加 lookup 約束
  2. Scaled Exp Gadget：算 y = ex × SF，用 lookup table
  3. Variable Division Gadget：處理分母是變數的除法，b = c × a + r

矩陣乘法優化：Freivalds' Algorithm

矩陣乘法 B = WA 直接做要 O(n³)；Freivalds 做法是：在電路外算好 B，電路內只驗證 Br = W(Ar)，把驗證成本降到 O(n²)。

白話理解：你不在電路裡重算整個矩陣乘法，而是用隨機向量 r 抽查結果。只要 r 真的隨機且在承諾之後產生，prover 就很難作弊。

區塊六：Optimizer 詳解

Optimizer 是核心。原因就是那句殘酷現實：Rows 必須是 2k。你多一點 row，可能就從 2k 跳到 2(k+1)，成本接近翻倍。

Optimizer 流程（Algorithm 1）

  1. BenchmarkOperations：在目標硬體上測 FFT、MSM、lookup 建表等操作的時間（只要做一次）
  2. GenerateLogicalLayouts：產生候選的邏輯布局（每一層要用哪種 gadget）
  3. GeneratePhysicalLayout：決定實際的 columns 數量
  4. FindOptimalK：找最佳的 k，讓 rows = 2k 且能裝下電路
  5. EstimateCost：用成本模型估算 proving time，挑成本最低的方案

Heuristic Pruning

候選空間會爆炸，所以要剪掉明顯不划算的選項。策略：傾向讓同類 layer 使用同一種實作，因為新增 constraint 的固定成本往往比新增 column 更貴。

Row-exact Simulator

你如果估 row 數估錯一點點，就可能被迫跳到下一個 2k，成本翻倍。所以它做 row-exact simulation，精準算出某個 layout 會用掉多少 rows。

成本模型

Proving time 主要來源是 FFT 與 MSM。重點不是算到毫秒，而是排序要準：誰比較快、誰比較慢，模型要能排出來。

多目標優化

Optimizer 可以選擇目標是「最短 proving time」或「最小 proof size」。在區塊鏈場景特別重要，因為鏈上儲存很貴。

區塊七：實驗結果

支援的模型（Table 5）

  • GPT-2：81.3M 參數、188.9M FLOPs
  • Twitter：48.1M 參數、96.2M FLOPs
  • Diffusion：19.5M 參數、22.9B FLOPs
  • VGG16：15.2M 參數（在 CIFAR-10）

實驗硬體環境

AWS EC2 r6i 系列。GPT-2 與 Diffusion 用到 1TB RAM。這反映一個現實：ZK proof 對記憶體需求非常高。

端到端效能重點數字（KZG）

  • MNIST：Proving 2.45 秒；Verification 6.69 毫秒
  • ResNet-18：Proving 52.9 秒；Verification 11.84 毫秒
  • GPT-2：Proving 約 61 分鐘；Verification 18.70 秒
關鍵觀察：Proving 很貴（幾秒到一小時）；Verification 通常便宜（毫秒級），但 GPT-2 例外；Proof size 約 6-28 KB。

量化後準確率（Table 8）

準確率損失不超過 0.01%，比一般量化方法的 0.1% 門檻還小很多。

消融實驗重點

有 Optimizer vs 固定配置：VGG16 改善 131%，GPT-2 改善 63%。

多樣化 gadgets 的重要性：拿掉額外 gadget 實現後，DLRM 慢到 24 倍，ResNet-18 慢 15 倍。

區塊八：結論與限制

四個限制

  1. 記憶體瓶頸：GPT-2 需要 1TB RAM
  2. 不支援動態控制流：沒有 branching 或 variable-length loops
  3. 模型架構需公開：權重可以私密，但 verifier 需要知道計算圖
  4. 無形式化驗證：TensorFlow 到電路的等價性未做形式化證明

五個 Takeaways

  1. zkML 的難點是「能不能跑得動」——halo2 理論上什麼都能表示，但性能是現實瓶頸
  2. 同一運算的等價表示，選錯差 24 倍——編譯加最佳化比想像的重要
  3. Softmax 是 Transformer 的關鍵門檻——ZKML 用三個 gadgets 解決
  4. Row 必須是 2k 讓全域布局選擇很關鍵——Row-exact simulator 是成功關鍵
  5. 現階段仍非常吃硬體資源——離「大型 LLM 每次推論都出 proof」還有距離

ZKML 把「可驗證 ML 推論」從只能 demo 小 CNN，推進到能處理更接近現實的模型類型，而且用「gadget 多樣性 + optimizer」把效能做出來。
