ZKML 口頭報告講稿

ZKML: An Optimizing System for ML Inference in Zero-Knowledge Proofs

各位好，今天我想報告的是一篇 EuroSys 2024 的系統論文，標題叫做 ZKML: An Optimizing System for ML Inference in Zero-Knowledge Proofs。

你可以把它理解成：作者做了一個系統，讓「機器學習推論」這件事，能用零知識證明（Zero-Knowledge Proof, ZKP）來證明「我真的照你說的那個模型算出答案」，而且還做了一個像編譯器一樣的最佳化器（optimizer），去自動挑出比較快、比較省的證明電路。

我今天會按照報告頁面的架構，一個區塊一個區塊往下走：研究動機、應用場景、技術背景、系統架構、Gadgets、Optimizer、實驗結果，最後是結論與限制。

我先講一個總結式的核心句，讓大家先抓住這篇的方向：

ZKML 的核心價值，是把「相信平台」改成「驗證平台」。

平台每次給你推論結果的同時，也給你一個 proof，讓你能驗證：這個輸出，確實是用「那個被承諾的模型」對輸入算出來的，而且在過程中不需要公開模型權重。

好，接下來我就照區塊開始。

* * *

區塊一：研究動機

先從問題背景開始。你先想一個很日常的場景：

你在使用某個大型平台，例如社群媒體、短影音、或是某個 AI 助手 API。你看到的內容排序、你收到的推薦、甚至你得到的答案，其實背後都是機器學習模型在做決策。

問題是，這些模型大多是部署在封閉系統（closed systems）或 API 後面。你看不到模型長什麼樣，也看不到它到底是不是照它宣稱的方式運作。

於是社會上就出現對「透明度」的要求：你可不可以公開模型權重？可不可以公開資料？可不可以讓大家查核你有沒有作弊？

但現實上公司通常不願意。原因很合理：

第一，資料可能牽涉隱私，例如醫療資料、用戶行為資料。

第二，模型權重可能是商業機密，訓練成本非常高。論文用 GPT 類模型做例子，強調這些權重不可能隨便公開。

那怎麼辦？這篇論文要做的就是：不要要求公開權重，但也不要完全相信平台。改用零知識證明：平台每次給你結果的同時，也給你一個 proof。

論文第一頁的 Figure 1 用 Twitter 推薦做示意：

沒有 ZKML 的時候，平台說它用模型 M 排序，但你無法知道它是不是偷偷用另一個模型 M'。

有了 ZKML 之後，平台每次輸出推薦結果時，也附上一個 ZKML proof，你就可以驗證「它真的用 M 算出來」。

這就是這篇的核心價值：把「相信平台」改成「驗證平台」。

但這裡也要特別提醒一點：ZKML 不證明什麼？

ZKML 不是在保證「模型是好的」，也不是在保證「模型是公平的」。

它主要保證的是：你說你用這個模型算，你就必須真的用這個模型算。

如果模型本身有偏見、有歧視、有品質問題，ZKML 不會神奇地消除它。它只是讓你能確定「平台沒有在計算過程上說謊」。

* * *

區塊二：應用場景

接下來進到「應用場景」，論文列了三個 use case，我用口語講成三句話：

第一，無信任審計（Trustless Audits）：

平台不公開權重，但承諾一個固定模型。每次推論都附 proof。第三方審計者就能驗證平台沒有偷換模型。你甚至可以把「算測試集準確率」也做成另一個可證明的審計電路，形成完整的端到端審計鏈。

第二，隱私生物辨識（Private Biometric Authentication）：

用戶想證明自己是真人、或證明身份，但不想把臉部特徵交出去。用 ZK proof 來證明「辨識結果確實由某模型算得」，並搭配具有硬體簽章的感測器（attested sensors）確保資料來源可靠。平台只驗證 proof，不需要拿到你的照片或生物特徵。

第三，無信任信用評分（Trustless Credit Scores）：

這個特別適合區塊鏈。用戶可以用私密資料或鏈上歷史特徵計算信用分數，再用 proof 證明分數是依照固定模型算出來的。鏈上只需要驗證 proof，不用看到你的隱私資料。

到這裡你會發現：ZKML 很像在替 AI 系統加一層「可驗證的誠實性」。

這三個應用有一個共同特性：它們要完整安全，通常需要結合其他技術，例如 verified databases、attested sensors。ZKML 專注的是「ML inference 的可驗證性」這一環。

區塊三：技術背景

接下來是技術背景。這個區塊主要要回答兩個問題：

第一，ZKML 在做 proof 的流程是什麼？

第二，它底層用的 halo2 電路模型，為什麼會讓「最佳化」變得很重要？

先看 ZKML 證明與驗證流程，請看 Figure 2(a)。

你先把模型編譯成電路（model circuit）。然後 prover 用電路對輸入做推論，同時產生 proof。最後 verifier 用 verifying key 驗證 proof，得到「verified」或「not verified」。

也就是說：推論結果不是只靠平台口頭說，而是有 proof 可以驗證。ZKML 的輸出除了 ML output 以外，還有 proof；Verifier 驗證後能確認結果是否可信。

接著講 halo2 的電路表示。

你可以先把 halo2 的電路想成一個超大的表格，像 Excel 一樣，是一個 2D grid。表格裡每一格 cell 都是一個有限域（finite field）上的數。

你在這個表格上要做的事，就是用各種「限制條件（constraints）」去限制這些格子必須符合某些等式。論文把 constraint 分三類：

第一，多項式約束（polynomial constraint）：對某些 cell 做多項式，要求結果等於零。白話就是「你必須滿足這條方程式」。

第二，複製約束（copy constraint）：強迫兩個 cell 值相等。白話就是「這兩格一定要一樣」。

第三，查表約束（lookup constraint）：強迫某些 cell 的組合必須出現在一個 lookup table 裡。白話就是「你只能從表裡挑合法值」。

然後 halo2 還有一個非常關鍵、非常影響效能的限制：

Row 的數量必須是 2 的冪，也就是 2^k。

這個限制會造成一個很殘酷的現實：你只要多用一點點 row，可能就從 2^k 被迫跳到 2^(k+1)，成本可能接近翻倍。所以電路布局（layout）不是「差一點點」的問題，而可能是「差一倍」的問題。

接著講一個關鍵發現：為什麼同一個運算會有很多表示法？

論文用 ReLU 當例子。ReLU 就是：輸入 x，小於 0 變 0，大於 0 保留。在 ZK 電路裡，你可以用兩種大方向做：

第一種，用多項式約束做位元分解（bit decomposition）：你把 x 展開成很多 bit，檢查符號位，然後重新組回去。好處是不需要 lookup table。壞處是會用掉很多 cell，大概要 b+2 個 cell（b 是位寬）。

第二種，用 lookup table：你直接建一張表，存所有可能的 x 對應的 ReLU(x)。在電路裡你只需要用很少 cell，做查表就好。但缺點是表會很大，至少 2^b 行，而且 lookup 本身也有額外成本。

最關鍵的是：哪個比較快，不是固定的。取決於你做多少次 ReLU、以及整個電路的 row/col 配置。

論文還做一個反直覺的例子：如果你只做一次 ReLU，建一張 lookup 表可能比直接用位元分解還貴。但如果你要做 2^18 次 ReLU，lookup 可能又比較省。

同一個運算，選不同表示法，性能可能差到 24 倍。所以你不能只看單一運算，要看整體。這就是全域最佳化。

區塊四：系統架構

接下來進到系統架構。這裡重點有三個：ZKML 的系統模組、KZG 跟 IPA 兩種 commitment scheme 的差異、以及 Optimizer 的整體工作流程。

先看 Figure 3，它畫了整個系統模組：

最底層是 halo2，這是底層的證明系統，支援 KZG 與 IPA 兩種 commitment scheme。

上面一層是低階 gadgets。Gadget 就是把 ML 推論常用的基本操作，做成電路世界的「積木」。例如 dot product、softmax、逐點非線性等等。

再往上是 ML layers，組成各種 ML 層，像 Fully connected、Conv2D、DepthwiseConv2D 等。ZKML 支援 43 種 layer。

核心是 aggregator 跟 layout optimizer。Aggregator 負責把 layers 變成整體電路；Layout Optimizer 負責挑電路布局。

最上面是 User Tools，提供 Prover、Verifier、Benchmark、Test 等工具，讓使用者可以用比較友善的方式跑完整流程。

有些模組用 Rust 實作，偏 halo2 與 proving；有些用 Python 實作，偏 ML 與 optimizer。

你可以把它理解成：ZKML 不只是把模型「翻譯」成電路，它還會「挑一種比較快的翻譯方式」。

接著講 KZG vs IPA。

KZG 的特點是：驗證通常很快，只要一次 pairing check。但需要一次性的通用可信設定（universal trusted setup）。論文說他們使用 PSE 的 Powers of Tau，支援到 2^28 rows，而且有 75+ 參與者，使用者就不用自己再跑一次 setup。

IPA 的特點是：透明（transparent），不需要 trusted setup。但通常 proof 會更大、驗證時間更長，要做 O(n) 的群運算。

所以你要選哪個？如果你在乎不需要 trusted setup，就偏 IPA。如果你在乎 verification 很快、特別像鏈上驗證，你可能偏 KZG。ZKML 的系統設計是兩個都支援。

最後是 Optimizer 流程，請看 Figure 4。

它把 ZKML optimizer 做成像資料庫 query optimizer 一樣的流程：

ML model specification 先變成 logical plans，再變成 physical plans，再做 cost estimation，最後挑最省的 plan。

到這裡，你就可以理解：ZKML 的核心不是只做「轉換」，而是做「轉換 + 最佳化」。

區塊五：Gadgets 設計

接下來進 Gadgets 設計。這裡我會分三段講：四大類 gadgets 是什麼、Softmax 為什麼難以及 ZKML 怎麼把它拆成三個 gadgets、矩陣乘法怎麼優化。

先講四大類 gadgets。

第一類，形狀操作（shape operations）：例如 reshape、slice、concat。這些操作在很多 tensor 框架裡只是改「view」或改索引。在 ZKML 裡也是一樣：你可以讓新的 tensor 只是引用原本 cell，所以不用新增 witness cell。論文直接說這類操作對 proving time 幾乎是「免費」的。

第二類，算術操作（arithmetic operations）：加法、減法、乘法、除法、dot product 等。關鍵不在於「有沒有支援加法」，而在於「你用哪種電路表示加法比較省」。所以 ZKML 不是只做一個版本，而是做很多版本，讓 optimizer 來選。

第三類，逐點非線性（pointwise non-linearities）：ReLU、sigmoid、tanh、exp 等。除了 ReLU 之外，很多非線性很難用多項式約束有效率地逼近，所以 ZKML 走 lookup table。

第四類，特化操作（specialized operations）：主要是為了 softmax。因為 softmax 在 Transformer 等模型非常關鍵，但在 ZK 電路裡很難做得又快又準。

接著就進到 Softmax 的突破。

Softmax 是向量函數，你不可能為整個向量直接建 lookup 表，表會爆炸。所以 ZKML 走常見的數值穩定技巧：先做 x_i 減掉 max_j x_j。這不改變 softmax 結果，因為 softmax 對整體平移不變（shift invariant），但能讓 exp 的輸入範圍變小，避免數值爆炸。

然後 ZKML 把 softmax 拆成三個關鍵 gadget：

第一個，最大值 gadget（maximum operator）：你要算 c 等於 max(a, b)。

先用一個多項式約束強迫 c 只能等於 a 或 b：也就是「(c-a)(c-b) = 0」。這代表 c 必須等於 a 或 c 必須等於 b。

但光這樣不夠，因為你還要確保 c 真的比較大。所以又加兩個 lookup：限制 c-a 與 c-b 必須落在 0 到 N 的範圍內。白話就是：c-a 不能是負的，c-b 也不能是負的。所以 c 同時大於等於 a、也大於等於 b。兩者合起來，c 就真的是最大值。

第二個，縮放指數 gadget（scaled exponentiation）：y 等於 exp(x) 乘上一個 scale factor SF。做法也是用 lookup：直接把 exp 的對應值查表出來，但把數值縮放到固定點表示。

第三個，變動除法 gadget（variable division）：這個很關鍵，因為 softmax 最後要除以總和，而分母不是固定值。

它的概念是把除法改寫成：b = c × a + r。也就是「商乘除數加餘數等於被除數」。然後約束餘數 r 落在合理範圍。要做四捨五入，就把公式轉成標準的整數除法形式。

這三個東西，最後就能拼出 softmax。這也是 ZKML 能支援 Transformer 類模型的重要原因之一。

講完 softmax 的三個 gadgets，最後是矩陣乘法優化：Freivalds' Algorithm。

全連接、卷積、batched matmul，本質上都大量用到矩陣乘法。如果你在電路裡「老實算矩陣乘法」，成本會非常大，是 O(n³)。

ZKML 用的技巧是 Freivalds' algorithm。白話就是：結果矩陣 B 先在電路外算好。電路內不重算 B，而是做一個隨機檢查：抽一個隨機向量 r，檢查 Br 是否等於 W(Ar)。這樣只要 O(n²) 的成本就能驗證矩陣乘法正確。

注意這個 r 不能讓 prover 先知道，所以必須在承諾之後產生，否則 prover 可以作弊。

區塊六：Optimizer 詳解

接下來是 Optimizer。

你可能會想：聽起來就是做了一堆 gadget，然後組起來而已。為什麼這篇會上 EuroSys 這種系統會？

關鍵在 optimizer。

因為在 halo2 裡，你不是只有一種方式表達同一個運算。你可以用不同 gadget、不同 lookup 設計、不同 column 數、不同 row 數。而 row 又必須是 2^k。所以同一個模型，可能有很多等價電路，性能差距非常大。

設計選擇會造成最高 24 倍的性能差距。沒有 optimizer，你很容易產生一個「能證明但慢到爆」的電路。

所以 Optimizer 要做的事情，是在很多等價表示中選一個「最省」的。

論文給了一個 Algorithm 1，我用口語講它做什麼：

第一步，先做硬體 benchmark（BenchmarkOperations）。它會測在你的硬體上：不同大小的 FFT 多久、不同大小的 MSM 多久、lookup table 建立多久。這步只要做一次，因為同一台機器結果差不多。

第二步，產生候選的邏輯布局（GenerateLogicalLayouts）。邏輯布局的意思是：決定每一層用哪些 gadget 實作，但還沒決定實際要幾個 columns、幾個 rows。

第三步，決定實際的 columns 數量（GeneratePhysicalLayout）。

第四步，找最適合的 k（FindOptimalK），因為 rows 必須是 2^k，所以要找最佳的 k，讓 rows = 2^k 且能裝下電路。

第五步，用成本模型估算 proving time（EstimateCost），挑成本最低的方案。

這裡還有一個很重要的細節：候選空間可能爆炸，所以 ZKML 用 heuristic pruning。關鍵 heuristic 是：傾向讓同類 layer 使用同一種實作，因為新增 constraint 的固定成本往往比新增 column 更貴，而混用不同實作帶來的收益常不值得。

接著是 Row-exact Simulator，為什麼「精準」很重要？

因為 rows 有 2^k 的門檻。你只要估錯，可能以為自己在 2^20 以內，實際上超出一點點，就被迫跳到 2^21，成本可能就差一倍。所以 row-exact simulation 是 optimizer 能做對決策的核心之一。

最後是成本模型。

Proving time 大頭是 FFT 與 MSM，外加 lookup 建表。Layout 一旦決定，電路統計量就決定，FFT/MSM 次數與大小就能被推導。再用硬體 benchmark 得到的「一次 FFT/MSM 多少時間」去算出總成本。

重點不是算到毫秒，而是排序要準：誰比較快，成本模型要能排得出來。

另外 optimizer 甚至可以切換目標，從「最短 proving time」切成「最小 proof size」。這對區塊鏈很重要，因為鏈上儲存很貴，你可能願意證明慢一點換 proof 小一點。

區塊七：實驗結果

接下來是實驗結果。這裡我會講四件事：支援哪些模型、端到端效能、量化後準確率掉多少、與先前工作比較及消融實驗。

先講支援的模型。你可以把它記成：從小模型 MNIST、到 CIFAR 的 ResNet-18、到 ImageNet 的 MobileNet、到推薦系統 DLRM 與 Twitter MaskNet、到小 diffusion、甚至到 distilled GPT-2。

硬體環境：他們用 AWS r6i 系列，因為 proving 很吃 RAM。例如 GPT-2 與 diffusion 用到 1TB RAM 的 r6i.32xlarge。這裡其實也反映一個現實：ZK proof 對記憶體需求非常高。

再來是端到端效能，我用口語挑幾個代表性的數字講。

KZG 後端：

MNIST：證明約 2.45 秒；驗證約 6.69 毫秒；proof 大小約 6.5 KB。

ResNet-18：證明約 52.9 秒；驗證約 11.84 毫秒；proof 大小約 15.7 KB。

Twitter：證明約 358.7 秒，大概 6 分鐘；驗證約 22 毫秒；proof 約 6.8 KB。

GPT-2：證明約 3651 秒，大概一小時；驗證約 18.7 秒；proof 約 28 KB。

Diffusion：證明也接近一小時；驗證不到 0.1 秒；proof 約 28 KB。

你會看到一個很清楚的趨勢：證明很貴，但驗證通常很便宜。而且 proof size 多數情況是 KB 到數十 KB，對於很多需要大量驗證的場景很有吸引力。

IPA 後端通常 proof size 比較大、verification 比較慢，因為不一樣的承諾與驗證成本結構；但在某些情況下 proving 可能略快，因為底層運算差異。

接著是量化後準確率。因為 ZK 電路裡通常用固定點（fixed-point），會有量化誤差，可能影響 accuracy。

MNIST、VGG16、ResNet-18 的 accuracy 幾乎不變，差異最多 0.01% 等級。作者還提到，高品質量化一般以 0.1% 內的變化為目標，他們比這個還小。這代表他們的 fixed-point 與 lookup 設計是成功的。

再來是與先前工作比較及消融實驗。

跟 zkCNN、vCNN 在 CIFAR-10 場景下比較，ZKML 多數指標表現更好，尤其 verification time 與 proof size 相對 zkCNN 有顯著優勢。

消融實驗是整篇最有說服力的部分：

把 ZKML 跟「固定配置」相比，optimizer 帶來顯著改善，像 VGG16 的 proving time 改善 131%。

把「多種 gadget 實作」拿掉，讓每層只有固定一種實作，但仍保留 optimizer，結果 proving time 可能慢到極端程度：例如 DLRM 出現 24 倍慢。這直接證明：不提供多樣化 gadget，optimizer 也救不了你。因為你沒有選擇空間，就只能踩到很爛的電路表示。

成本估算的 ranking 準確度用 Kendall's tau 量，KZG 0.89、IPA 0.88。白話就是：成本模型在「排序誰比較快」這件事上很可靠。

* * *

區塊八：結論與限制

最後進到結論與限制。論文很誠實地列出限制：

第一，記憶體與硬體仍是瓶頸。要證明最大模型（distilled GPT-2）需要到 1TB RAM 等級。這不是一般人隨手可跑。

第二，不支援 branching 或 variable-length loops。換句話說，你需要固定長度輸入；NLP 變長輸入要 padding，分支與迴圈要 unroll。這會帶來效率損失。

第三，模型架構要公開。權重可私密，但 verifier 要知道你證明的是什麼計算圖。作者認為 open-source 模型趨勢下很多場景可接受，但在某些商業情境，架構也可能敏感。

第四，電路正確性沒有形式化證明。也就是：你把 TensorFlow 模型翻譯成電路，是否嚴格等價？這是 zkML 系統普遍的大問題。論文承認沒有做形式化證明。

最後我用五個 takeaways 收尾，讀完這篇最值得記住的五句：

第一，zkML 的難點不是「能不能表示」，而是「能不能跑得動」。halo2 理論上什麼都能表示，但性能是現實瓶頸。

第二，同一個運算在電路裡有很多等價表示，選錯會差到 24 倍。所以「編譯 + 最佳化」比你想像的重要。

第三，softmax 是走向 Transformer/LLM 的關鍵門檻。ZKML 透過 max、scaled exp、variable division，再加上數值穩定技巧，把 softmax 變得可用。

第四，optimizer 的核心是：row 必須是 2 的冪，這讓全域布局選擇變得非常關鍵。Row-exact simulator + cost model 是它能成功挑出好方案的原因。

第五，現階段仍非常吃硬體資源，尤其大模型。ZKML 把邊界推進了，但離「大型 LLM 每次推論都出 proof」還有距離；未來需要更高效 proving system、更強硬體與更多工程最佳化。

一句話收尾：ZKML 把「可驗證 ML 推論」從只能 demo 小 CNN，推進到能處理更接近現實的模型類型，而且用「gadget 多樣性 + optimizer」把效能做出來。

以上就是我今天的報告，謝謝大家。

四、關鍵觀察

1. Proving 時間仍是主要瓶頸

即使到 2025 年，13B 參數 LLM 的 proving 時間仍需約 15-45 分鐘。對於即時應用（如聊天機器人）尚不可行，但對於高價值決策的異步驗證已具實用性。

2. 專用協議 vs 通用框架

zkLLM 專為 LLM 設計（引入 tlookup、zkAttn），在 13B 模型上達到 <15 分鐘；而通用框架如 ZKTorch 在 7B 模型需 44 分鐘。專用協議在特定場景更有效率，但通用性較差。

3. Proof Size 差異顯著

zkLLM 維持 <200 KB 的小 proof；ZKTorch 在大模型上的 proof 可達 20+ MB。這對區塊鏈上鏈驗證的成本影響很大。

4. GPU 加速成為標配

zkLLM 使用 CUDA 實現，ZKTorch 與 EZKL 也都支援 GPU。CPU-only 的傳統做法已不適用於大模型。

趨勢總結：從 2024 到 2025，ZKML 領域的 proving 時間約有 5-10× 的改善（視模型與系統而定），但 100B 參數以上的 LLM 可驗證推論仍是開放挑戰。
