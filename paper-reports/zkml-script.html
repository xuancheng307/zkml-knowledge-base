ZKML 口頭報告講稿

ZKML: An Optimizing System for ML Inference in Zero-Knowledge Proofs

大家好，今天我想報告的主題是 ZKML——全名是「ZKML: An Optimizing System for ML Inference in Zero-Knowledge Proofs」，中文我會稱它是「零知識證明機器學習推論最佳化系統」。

我今天的講法會完全按照我這份報告頁面上的架構，一個區塊一個區塊往下走。你如果有在看投影片或網頁，也會發現順序是一樣的：研究動機、應用場景、技術背景、系統架構、Gadgets、Optimizer、實驗結果，最後是結論與限制。

我先講一個總結式的核心句，讓大家先抓住這篇的方向：

ZKML 的核心價值，是把「相信平台」改成「驗證平台」。

也就是：模型提供者每次給你推論結果的同時，還會給你一個零知識證明（Zero-Knowledge Proof, ZKP），讓你可以驗證這個結果確實是由「事先承諾的模型」算出來的，而且在過程中不需要公開模型權重。

好，接下來我就照區塊開始。

* * *

區塊一：研究動機

先從問題背景開始。

現在很多機器學習模型（Machine Learning, ML）其實都部署在封閉系統（closed systems）或 API 後面。使用者拿到的只是「輸入 → 輸出」的服務，你看不到模型裡面到底怎麼做決策。

這件事不只是在學術上有趣，它實際上會影響很具體的生活與社會決策。例如：

第一，社群媒體推薦系統會影響你看到的資訊流。

第二，醫療診斷 AI 會影響重大決策。

第三，信用評分模型會影響貸款審批。

當這些模型越來越重要，大家自然就會要求透明度（transparency）與可驗證性（verifiability）。

最直覺的做法，就是把模型權重（model weights）公開，把資料公開。

但這裡就出現報告頁面上寫的「核心矛盾」：

使用者想要透明、可驗證；

企業端卻有合理顧慮，包含隱私與商業機密。

我用更白話的方式說：很多模型是用私密資料訓練的，你不可能要求它把訓練資料全摊開；而且模型權重本身可能是公司花極大成本訓練出來的資產，不會輕易公開。

這時候，ZKML 想解的就是：我不要你公開權重，但我也不要完全「相信你」。

我希望你用零知識證明來「證明你沒騙我」。

這裡請大家看一下報告頁面上的 Figure 1，它用 Twitter 推薦作為例子。

沒有 ZKML 的時候，平台說它用模型 M 幫你排序推薦內容，但你其實無法確認它是不是偷偷用另一個模型 M'。

有了 ZKML 之後，平台除了給你「Interesting tweets？」的推薦結果，還會附上一個「ZKML proof」。

你就可以驗證：這個輸出確實是由你期待的模型 M 算出來的，而不是員工臨時插手、或平台偷偷換模型。

所以在這個區塊的最後，我把 ZKML 的核心價值再唸一次：

把「相信平台」改成「驗證平台」，平台每次給你結果時，也給你 proof，證明輸出確實來自承諾的模型。

但同一個區塊也特別提醒一點：ZKML 不證明什麼？

它不保證模型是「好的」或「公平的」；

它只保證「平台沒有在計算過程上說謊」。

也就是說，如果模型本身偏誤（bias）很大，ZKML 不會神奇地讓它變公平。

ZKML 解的是「誠實性」與「可驗證性」，不是「價值判斷」。

* * *

區塊二：應用場景

接下來進到「應用場景」，這裡報告頁面列了三個典型用途。我會依序講：無需信任的審計、隱私生物辨識、可驗證信用評分。

第一個是 Trustless Audits，也就是「無需信任的審計」。

問題是什麼？很多 ML 模型訓練在私人數據上，例如推薦系統。

使用者想審計：你是不是照你說的規則運作？你是不是偷偷改模型？你是不是在特定族群上做差別待遇？

但企業又不能公開權重與資料。

ZKML 的解法是：模型提供者先 commit 到固定模型，之後每次輸出都附 ZK proof。

你不用看到權重，但你可以驗證它確實用那個承諾模型產生結果。

如果再結合 verified databases（可驗證資料庫）之類的技術，就可以把「資料來源」到「推論過程」到「審計算法」串成端到端（end-to-end）的可驗證鏈。

第二個是 Private Biometric Authentication，也就是「隱私生物辨識」。

問題是：線上服務想確認你是真人，但很多生物辨識方案侵犯隱私，因為你要把臉、指紋、聲紋交給平台。

報告頁面提到的做法是結合 attested sensors——也就是帶有硬體簽章（digital signature）的感測器。

使用者在本地拍照或感測，感測器對資料簽章，然後本地跑人臉比對模型，最後產生 ZK proof。

平台只驗證 proof，不需要拿到你的照片或生物特徵，但仍然能得到「確實比對成功」這件事的可信保證。

第三個是 Trustless Credit Scores，也就是「可驗證信用評分」。

這個很常出現在區塊鏈場景，尤其是 undercollateralized loans（不足額抵押貸款）。

貸方想知道借方信用如何，但借方不想把完整財務與行為資料公開。

做法是：用戶可以用 on-chain history（鏈上歷史）或其他受控資料計算信用分數，再用 ZK-SNARK 證明這個分數確實依照承諾的 ML 模型誠實計算。

這樣借貸雙方都能驗證分數沒有被篡改，同時敏感資料不必公開。

這三個應用最後有一個「共同特性」，報告頁面也寫得很清楚：

它們要完整安全，通常需要結合其他技術，例如 verified databases、attested sensors。

ZKML 專注的是「ML inference 的可驗證性」這一環。

區塊三：技術背景

接下來是技術背景。這個區塊主要要回答兩個問題：

第一，ZKML 在做 proof 的流程是什麼？

第二，它底層用的 halo2 電路模型，為什麼會讓「最佳化」變得很重要？

先看 ZKML 證明與驗證流程。

報告頁面有 Figure 2(a)，把它拆成三個階段：

第一階段，Model Compilation：把模型編譯成電路（circuit）。

第二階段，ZKML Proving：把「輸入 + 電路」丟給 Prover，產生 Proof。

第三階段，ZKML Verification：Verifier 用 verifying key 驗證 proof，得到「verified」或「not verified」。

也就是：推論結果不是只靠平台口頭說，而是有 proof 可以驗證。

同一張圖也會看到：ZKML 的輸出除了 ML output 以外，還有 proof；Verifier 驗證後能確認結果是否可信。

接著報告頁面講 halo2 的電路表示。

它把電路想成一個 2D grid，也就是二維格子表格。每個 cell 裡面是一個有限域（finite field）元素。

然後，用 constraint（約束）把這些 cell 綁起來，確保它們符合你想要的運算規則。

報告頁面把約束分成三類，我照著念重點，並用一句話口語化：

第一，多項式約束（polynomial constraint）：要求某個多項式算出來要等於零，也就是「你必須滿足某條等式」。

第二，複製約束（copy constraint）：要求兩個 cell 值要一樣，也就是「這兩格必須相等」。

第三，查表約束（lookup constraint）：要求某些值必須出現在預先定義的表裡，也就是「你只能從合法表格裡選值」。

這裡有一個非常關鍵、也會影響後面所有最佳化的限制：Rows 必須是 2^k。

也就是 row 數只能是 2 的冪次方。

為什麼這會很重要？

因為你只要 row 數稍微超過 2^k 一點點，你可能就得跳到 2^(k+1)，整體成本可能接近翻倍。

所以在 halo2 這種系統裡，「電路布局（layout）」跟「電路大小（grid size）」不是細節，它直接決定你證明快不快。

接著報告頁面給一個關鍵發現：

同一運算，選錯實現方式，效能可能差 24 倍。

它用 ReLU 當例子。

ReLU 有兩種常見電路做法：

方法一：位元分解（bit decomposition）。

把 x 展開成 bit，檢查符號位，再重組。優點是不需要 lookup table；缺點是很吃 cell，位寬 b 的話要 b+2 個 cell。

方法二：Lookup Table。

直接建表存 (x, ReLU(x)) 的對應，電路內只要少量 cell 就能查表；但表大小至少 2^b 行，而且 lookup 本身也有成本。

哪個快？不一定。

如果只做一次 ReLU，做 lookup 可能反而更貴；

但如果做很多次 ReLU，lookup 的攤提成本可能更划算。

報告頁面還特別寫：只做 1 次 ReLU 時 lookup 可能更貴；做 2^18 次時 lookup 可能更省。

這句話其實就是在鋪陳：最佳化是全域問題，不是局部問題。

區塊四：系統架構

接下來進到系統架構。這裡重點有三個：

第一，ZKML 的五層架構。

第二，KZG 跟 IPA 兩種 commitment scheme 的差異。

第三，Optimizer 的整體工作流程。

先看 Figure 3：ZKML 五層架構。

我照著表格把每一層的角色講清楚。

最底層是 ZK Backend：底層證明系統使用 halo2，並支援 KZG 與 IPA 兩種 commitment schemes。

往上一層是 Low-level Gadgets：它把常用運算做成電路積木，分成 Shape operations、Arithmetic operations、Non-linearities、Specialized operations。

再往上一層是 Logical Layers：也就是 ML 層抽象，像 Fully connected、Conv2D、DepthwiseConv2D 等。

再往上一層是 Core：核心模組包含 Aggregator 跟 Layout Optimizer。

Aggregator 負責把 layers 組成完整 halo2 電路；

Layout Optimizer 負責選最有效率的佈局。

最上面是 User Tools：提供 Prover、Verifier、Benchmark、Test 等工具，讓使用者可以用比較友善的方式跑完整流程。

這張圖裡也特別標示：有些模組用 Rust 實作，偏 halo2 與 proving；有些用 Python 實作，偏 ML 與 optimizer。

我用一句話總結這張圖：ZKML 不是只有「能做電路」，它是一整個「從模型到最佳電路、再到 proof 與驗證」的系統。

接著講 KZG vs IPA。

報告頁面用兩張卡片比較，我照重點唸：

KZG Commitment：

需要 Trusted Setup，一次性的通用可信設定；報告頁面提到 PSE 已完成 2^28，超過 75 位參與者。

優點是 proof size 較小，驗證極快，基本上是一個 pairing check。

適合：你很在乎驗證速度，而且可接受 trusted setup 的場景。

IPA Commitment：

它是 transparent，不需要 trusted setup。

但 proof size 較大，verification 較慢，通常要做 O(n) 的群運算。

適合：你更在乎去中心化與透明性，不想依賴 trusted setup 的場景。

也就是：這兩種後端沒有絕對好壞，是你要的安全模型與部署場景不同。

最後是 Optimizer 流程，請看 Figure 4。

這張圖把 ZKML optimizer 講得很像「編譯器」或「資料庫 query optimizer」：先有規格，再有 plan，再選成本最低的。

它的四階段是：

第一，ML Model Specification：解析模型結構。

第二，Logical Plans：選每個運算、每一層要用哪種 gadget 實現。

第三，Physical Plans：決定電路佈局，包含 columns、rows 等配置。

第四，Cost Estimation：估算證明時間，選最佳方案。

到這裡，其實你就可以理解：ZKML 的核心不是只做「轉換」，而是做「轉換 + 最佳化」。

區塊五：Gadgets 設計

接下來進 Gadgets 設計。這裡我會照報告頁面分三段講：

第一，四大類 gadgets 是什麼。

第二，Softmax 為什麼難，以及 ZKML 怎麼把它拆成三個 gadgets。

第三，矩陣乘法怎麼優化：Freivalds' Algorithm。

先講四大類 gadgets。

第一類是 Shape：例如 reshape、slice、concat。

報告頁面直接寫它們幾乎是 Free，原因是 tensor 可以引用已存在的 cells，所以只是重排索引，不用新增 witness cells。

第二類是 Arithmetic：加減乘除、dot product 等。

這裡的重點不是「支援哪些運算」而已，而是「同一運算可以有多種電路寫法」，ZKML 會提供多種實作版本，讓 optimizer 挑。

第三類是 Non-linear：像 ReLU、sigmoid、tanh。

報告頁面提到多數非線性用 lookup table 做，因為用多項式約束去逼近會很不效率。

第四類是 Specialized：主要是為了 Softmax。

因為 Softmax 在 Transformer 這類現代模型非常關鍵，但在 ZK 電路裡很容易變得又慢又不準。

接著就進到 Softmax 的突破。

報告頁面先寫 Softmax 公式：y_i = e^{x_i} / Σ e^{x_j}。

它直接說一個關鍵困難：Softmax 是向量函數，沒辦法直接用 lookup table 表示整個向量，否則表的大小會爆炸。

所以 ZKML 用兩個策略：

第一，使用數值穩定技巧（Numerical Stability Trick）：先減掉最大值。

也就是 softmax(x_i) = softmax(x_i - max_j x_j)。

這樣 exponentials 的輸入都會 ≤ 0，比較不會 overflow，而且因為 softmax shift invariant，結果不變。

第二，把 Softmax 分解成三個可驗證的 gadgets：

第一個 gadget：Maximum Gadget，用來找最大值 c = max(a, b)。

它的約束分兩部分：

(1) 用多項式約束 (c-a)(c-b)=0，逼迫 c 只能等於 a 或 b。

(2) 用 lookup 約束 c-a ∈ [0, N)，c-b ∈ [0, N)，確保 c ≥ a 且 c ≥ b。

兩段加起來，c 就真的是最大值。

第二個 gadget：Scaled Exp Gadget，用來算 y = e^x × SF，其中 SF 是 scale factor。

用 lookup table 把 exp 對應值查出來，同時乘上縮放因子避免精度損失。

第三個 gadget：Variable Division Gadget，用來處理分母是變數的除法。

報告頁面寫：處理 c = Round(b/a)，其中 a 不是固定常數。

它的核心約束是：b = c × a + r，其中 r 是餘數，並要求 r 落在合理範圍內。

然後 rounding 的技巧是把 Round(b/a) 轉成 floor((2b + a) / 2a)，把四捨五入轉成標準整數除法形式。

講完 softmax 的三個 gadgets，最後是矩陣乘法優化：Freivalds' Algorithm。

報告頁面用一句話點出：

矩陣乘法 B = W A 直接做要 O(n^3)；

Freivalds 做法是：在電路外算好 B，電路內只驗證 B r = W (A r)，把驗證成本降到 O(n^2)。

我補一個白話理解：你不在電路裡重算整個矩陣乘法，而是用隨機向量 r 抽查結果。

只要 r 真的隨機且在承諾之後產生，prover 就很難作弊。

區塊六：Optimizer 詳解

接下來是 Optimizer。報告頁面在這裡的態度很明確：Optimizer 是核心。

原因其實就是我前面提過的那句殘酷現實：Rows 必須是 2^k。

你多一點 row，可能就從 2^k 跳到 2^{k+1}，成本接近翻倍。

所以 Optimizer 要做的事情，是在很多等價表示中選一個「最省」的。

報告頁面整理 Optimizer 流程（Algorithm 1）成表格，我照步驟講：

第一步：BenchmarkOperations。

在目標硬體上測 FFT、MSM、lookup 建表等操作的時間。這一步通常只要做一次。

第二步：GenerateLogicalLayouts。

產生候選的邏輯布局，也就是：每一層要用哪種 gadget 實作，但還不決定 columns 與 rows。

第三步：GeneratePhysicalLayout。

決定實際的 columns 數量。

第四步：FindOptimalK。

因為 rows 必須是 2^k，所以要找最佳的 k，讓 rows = 2^k 且能裝下電路。

第五步：EstimateCost。

用成本模型估算 proving time，挑成本最低的方案。

報告頁面也提到 heuristic pruning，也就是啟發式剪枝。

核心想法是：候選空間會爆炸，所以要剪掉明顯不划算的選項。

它舉的策略是：傾向讓同類 layer 使用同一種實作，因為新增 constraint 的固定成本往往比新增 column 更貴，而混用不同實作帶來的收益常不值得。

接著是 Row-exact Simulator。

報告頁面強調「精準」的重要性：你如果估 row 數估錯一點點，就可能被迫跳到下一個 2^k，成本翻倍。

所以它做 row-exact simulation，精準算出某個 layout 在某個 columns 設定下會用掉多少 rows。

最後是成本模型。

報告頁面說 proving time 主要來源是 FFT 與 MSM，再加上 lookup 建表與 field operations。

它還寫了一個簡化公式：C_FFT = n_FFT × t_FFT(k) + n'_FFT × t_FFT(k')。

重點不是算到毫秒，而是排序要準：誰比較快、誰比較慢，模型要能排出來，optimizer 才能選到接近最好的配置。

另外報告頁面也寫到多目標優化：Optimizer 可以選擇目標是「最短 proving time」或「最小 proof size」。

這在區塊鏈場景特別重要，因為鏈上儲存很貴，你可能願意證明慢一點換 proof 小一點。

區塊七：實驗結果

接下來是實驗結果。這裡我會照報告頁面順序講四件事：

第一，支援哪些模型。

第二，端到端效能：KZG 與 IPA 各自的 proving、verification、proof size。

第三，量化後準確率掉多少。

第四，與先前工作比較與消融實驗。

先講支援的模型，報告頁面引用 Table 5，列出幾個代表：

GPT-2：81.3M 參數、188.9M FLOPs。

Twitter：48.1M 參數、96.2M FLOPs。

Diffusion：19.5M 參數、22.9B FLOPs。

VGG16：15.2M 參數（在 CIFAR-10）。

另外還有 MobileNet、ResNet-18、DLRM、MNIST 等。

接著是實驗硬體環境。

報告頁面寫：在 AWS EC2 r6i 系列上測量。

大多數模型用 r6i.8xlarge：32 vCPU、256GB RAM。

MobileNet 用 r6i.16xlarge：64 vCPU、512GB RAM。

GPT-2 與 Diffusion 用 r6i.32xlarge：128 vCPU、1TB RAM。

這裡其實也反映一個現實：ZK proof 對記憶體需求非常高。

再來是端到端效能，先講 KZG 後端（Table 6）。

我直接唸幾個代表性的數字：

MNIST：Proving time 2.45 秒；Verification time 6.69 毫秒；Proof size 6,560 bytes。

ResNet-18：Proving 52.9 秒；Verification 11.84 毫秒；Proof size 15,744 bytes。

VGG16：Proving 637.14 秒，約 11 分鐘；Verification 9.62 毫秒；Proof size 12,064 bytes。

MobileNet：Proving 1,225.5 秒，約 20 分鐘；Verification 17.67 毫秒；Proof size 17,664 bytes。

Twitter：Proving 358.7 秒，約 6 分鐘；Verification 22.41 毫秒；Proof size 6,816 bytes。

Diffusion：Proving 3,600.57 秒，約 60 分鐘；Verification 92.78 毫秒；Proof size 28,704 bytes。

GPT-2：Proving 3,651.67 秒，約 61 分鐘；Verification 18.70 秒；Proof size 28,128 bytes。

報告頁面也有「關鍵觀察」：

Proving 很貴，從幾秒到一小時；

Verification 通常便宜，KZG 下多數模型是毫秒級，但 GPT-2 例外，驗證到 18.70 秒；

Proof size 大約 6 到 28 KB。

接著看 IPA 後端（Table 7），同樣我唸幾個代表數字：

MNIST：Proving 2.36 秒；Verification 22.26 毫秒；Proof size 7,680 bytes。

ResNet-18：Proving 46.5 秒；Verification 0.20 秒；Proof size 17,120 bytes。

VGG16：Proving 619.4 秒；Verification 2.49 秒；Proof size 17,184 bytes。

Twitter：Proving 364.9 秒；Verification 2.28 秒；Proof size 8,448 bytes。

GPT-2：Proving 3,949.60 秒；Verification 11.98 秒；Proof size 16,512 bytes。

報告頁面也總結：IPA 通常 proof size 比較大、verification 比較慢，因為不一樣的承諾與驗證成本結構；

但在某些情況下 proving 可能略快，因為底層運算差異。

接著是量化後準確率（Table 8）。

報告頁面說：ZKML 使用 fixed-point quantization，把浮點轉成有限域運算。

大家關心的是：準確率會不會掉？

它列了三個模型：

MNIST：FP32 99.06%，ZKML 99.06%，差異 0%。

VGG16：FP32 90.36%，ZKML 90.37%，差異 +0.01%。

ResNet-18：FP32 91.88%，ZKML 91.87%，差異 -0.01%。

也就是：準確率損失不超過 0.01%。

報告頁面還補一句：一般高品質量化通常以 0.1% 內變化為目標，他們比這門檻還小很多。

再來是與先前工作比較（Table 9）。

在 CIFAR-10 場景下：

zkCNN：Accuracy 90.3%；Proving 88.3 秒；Verify 59 毫秒；Proof 341 KB。

vCNN：Accuracy 90.4%（估計）；Proving 31 小時（估計）；Verify 20 秒；Proof 0.34 KB。

ZKML（ResNet-18）：Accuracy 91.9%；Proving 52.9 秒；Verify 12 毫秒；Proof 15.3 KB。

ZKML（VGG-16）：Accuracy 90.4%；Proving 584.1 秒；Verify 16 毫秒；Proof 12.1 KB。

報告頁面強調：ZKML 在驗證速度與 proof 大小上相對 zkCNN 有明顯優勢；而 vCNN 的 proof 非常小，但 proving 非常慢。

最後是消融實驗（ablation）。

報告頁面先講 Optimizer vs Fixed configuration（Table 10）。

例如：

MNIST：2.5 秒 vs 4.4 秒，改善 76%。

ResNet-18：52.9 秒 vs 74.8 秒，改善 41%。

VGG16：637.1 秒 vs 1474.0 秒，改善 131%。

GPT-2：3651.7 秒 vs 5952.0 秒，改善 63%。

這裡的訊息是：有 optimizer，效能差很多。

再來是「多樣化 gadgets 的重要性」（Table 11）。

把額外 gadget 實現拿掉，保留 optimizer，會怎樣？

MNIST：2.5 秒變 6.2 秒，慢 2.5 倍。

DLRM：34.4 秒變 859.5 秒，慢到 24 倍。

ResNet-18：52.9 秒變 812.6 秒，慢 15 倍。

這就直接支持它前面那句話：同一運算的不同實現，選錯真的可能差到 24 倍。

報告頁面也補充 optimizer 本身的效率：用 cost model 預測，不用窮舉全 benchmark。

例如 MNIST：optimizer 6.3 秒，但窮舉 benchmark 3,622 秒。

GPT-2：optimizer 185.3 秒，但窮舉 benchmark 估計要 1,078,449 秒。

所以 optimizer 能在很短時間內找到接近最好的配置。

區塊八：結論與限制

最後我進到結論與限制。報告頁面列了四個限制，我照順序講：

第一，記憶體瓶頸。

像 GPT-2 需要 1TB RAM，這不是一般環境可輕易做到。

第二，不支援動態控制流。

也就是沒有 branching 或 variable-length loops。

對 NLP 這類可變長輸入，通常需要固定長度、padding，或把分支與迴圈 unroll。

第三，模型架構需公開。

權重可以私密，但 verifier 需要知道你證明的計算圖與配置。

第四，無形式化驗證。

也就是 TensorFlow 到電路的等價性未做形式化證明；這是 zkML 類系統普遍難題。

最後報告頁面給五個 takeaways，我在結尾把它當作總結：

第一，zkML 的難點是「能不能跑得動」——halo2 理論上什麼都能表示，但性能是現實瓶頸。

第二，同一運算的等價表示，選錯差 24 倍——編譯加最佳化比想像的重要。

第三，Softmax 是 Transformer 的關鍵門檻——ZKML 用三個 gadgets 解決。

第四，Row 必須是 2^k 讓全域布局選擇很關鍵——Row-exact simulator 是成功關鍵。

第五，現階段仍非常吃硬體資源——離「大型 LLM 每次推論都出 proof」還有距離。

我用一句話收尾：ZKML 把「可驗證 ML 推論」從只能 demo 小 CNN，推進到能處理更接近現實的模型類型，而且用「gadget 多樣性 + optimizer」把效能做出來。

以上就是我今天的報告，謝謝大家。
