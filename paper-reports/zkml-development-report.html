一、問題場景

想像你是一家醫院的資訊主管，想用雲端 AI 服務分析病人的 X 光片。流程很簡單：上傳影像 → 雲端跑模型 → 回傳結果。

誠實性問題

雲端宣稱用 99% 準確度模型，但你怎麼知道？

  • 可能偷換便宜小模型
  • 可能根本沒跑模型
  • 你無法分辨

隱私問題

病人影像是高度敏感資料

  • 雲端能看到所有資料
  • 隱私法規風險
  • 病人信任問題

ZKML 的目標

讓你可以驗證 AI 推論的正確性，同時保護敏感資料不被洩漏

流程說明

  1. ML Client（左側）從資料庫取得輸入資料 x，發送給服務提供者
  2. ML Service Provider（右側）收到 x 後，讀取模型權重 w，執行推論 r = W(x, w)
  3. 服務提供者接著生成零知識證明 π，證明「輸出 r 確實是用模型 w 對輸入 x 計算出來的」
  4. 客戶端收到結果 r 和證明 π，執行 ZKP Verification 驗證正確性

關鍵：模型權重 w 是 private witness（私密見證），驗證者無法得知 w 的內容，只能確認計算正確。

二、什麼是機器學習推論

訓練階段

用大量資料調整參數，產生「模型權重」（數百萬～數十億浮點數）

推論階段 ← ZKML 關注

拿訓練好的模型處理新資料，做一次「前向傳播」得到輸出

神經網路的基本層

層類型 運算 對 ZK 的友善度
全連接層 y = Wx + b（矩陣乘法 + 加法） 友善 只有乘加
卷積層 滑動卷積核做點積 友善 展開成乘加
ReLU max(0, x) 困難 需要比較
Max Pooling 區塊取最大值 困難 多值比較
Softmax 指數 + 除法 困難 非算術運算

關鍵分類

線性層（全連接、卷積）：只需乘法和加法，ZK 友善

非線性層（ReLU、MaxPool、Softmax）：需要比較或複雜運算，是 ZKML 最大挑戰

三、為什麼把 ML 放進 ZK 很難

ZK 證明系統工作在有限域上，只有加法和乘法。但 ML 需要浮點數、除法、比較...

3.1 數值表示問題

神經網路用 float32

可表示非常大/小的數字，也可以表示小數

ZK 電路用有限域

元素是整數，沒有小數。運算超過模數 p 會「繞回來」

解法：量化 + 定點數

  • 定點數：約定小數點位置，如乘以 2^16，1.5 → 98304
  • 量化：float32 → int8，範圍 [-128, 127]

代價：損失精度，模型準確度可能下降

圖片說明（三個部分）

(a) 純整數推論：量化後的計算流程。輸入和權重都是 uint8（8 位元整數），卷積後用 32 位元累加器相加偏置，最後經過 ReLU6 輸出 uint8。全程只有整數運算。

(b) 模擬量化訓練：訓練時仍用 float32，但在權重和激活值後面插入「量化模擬節點」（wt quant / act quant），讓模型學會適應量化帶來的誤差。

(c) 精度與延遲的權衡：右側散點圖比較 float（紅點）和 8-bit 量化（藍方塊）在 ImageNet 上的表現。可以看到量化雖然稍微降低準確度，但大幅降低推論延遲。

3.2 非線性操作問題（最大瓶頸）

以 ReLU 為例：ReLU(x) = max(0, x)，需要判斷 x 是正還是負。

位元分解方法

把數字分解成 k 個位元，檢查最高位元判斷符號

  • 每個位元需約束：b × (1-b) = 0
  • 位元組合約束：x = b₀ + 2×b₁ + ... + 2^(k-1)×b_(k-1)

成本：k=64 時，每個 ReLU 需要 64 個變數 + 65 個約束

典型 CNN：幾十萬個 ReLU → 幾百萬個額外約束

四、早期的三種解法

1. 多項式近似

用低次多項式代替 ReLU（如 x²）

優點 只剩加乘

缺點 改變模型語義

2. 位元分解

分解成位元做範圍證明

優點 保留語義

缺點 成本極高

3. 查表 (Lookup)

預計算輸入輸出對應表

優點 保留語義、效率好

缺點 表格大小限制

關鍵認知

「ZK 保證的是你定義的 relation 的正確性。但如果你用近似或量化，relation 的語義本身就變了。」

這是 ZKML 設計必須面對的 trade-off：在「證明效率」和「語義精確度」之間取捨。

五、可驗證計算 vs 零知識

Verifiable Computation（可驗證計算）

重點：「算對沒」

Verifier 可以確認計算正確，但 Prover 可能需要公開所有輸入和中間值

Zero-Knowledge（零知識）

重點：「算對且不洩漏」

Verifier 只知道「計算正確」，不知道輸入和中間值

歷史脈絡

早期（~2017）先做「可驗證」，之後才加入「零知識」性質。所以早期論文有些強調 verifiable，有些強調 zero-knowledge。

六、三種隱私配置

類型 模型 輸入 典型場景
Type A 公開 私密 醫療診斷（保護病人資料）
Type B 私密 公開 商業 API（保護模型 IP）
Type C 私密 私密 金融風控（完全隱私）

情境說明

以 Twitter 推薦系統為例，使用者想知道「我看到的推文是被公平排序的嗎？」

上半部（沒有 ZKML）：使用者問「有什麼有趣的推文？」，Twitter 回傳「ZK is cool」。但使用者無法確認這是用哪個模型（M 或 M'）產生的推薦——可能是公開宣稱的模型 M，也可能是另一個模型 M'。

下半部（有 ZKML）：同樣的請求，但這次回傳時附帶 ZKML Proof。使用者可以驗證這個證明，確認推薦結果確實是用模型 M（而非其他模型）計算出來的。

七、ZKML 的形式化定義

Statement / Witness / Relation 框架

  • Statement（公開）：輸出 y、模型承諾 C
  • Witness（私密）：模型權重 w、輸入 x、中間值
  • Relation：約束關係，R(statement, witness) = 1 當且僅當計算正確

推論正確性的 Relation

R_infer = { (statement, witness) : statement = (模型承諾 C, 輸出 y) witness = (模型權重 w, 輸入 x, 中間值) 且 Commit(w) = C 且 Forward(w, x) = y }

準確度證明的 Relation

R_acc = { (statement, witness) : statement = (模型承諾 C, 測試集承諾 D, 準確度門檻 τ) witness = (模型權重 w, 測試資料) 且 Commit(w) = C 且 Commit(測試資料) = D 且 Accuracy(w, 測試資料) ≥ τ }

流程走一遍

  1. ① 承諾階段：Prover（P）持有 Model 和 Data，先對它們做承諾（commit）
  2. ② 設置階段：根據任務 Task 執行 Setup，產生 proving.key 和 verification.key
  3. ③ 執行推論：P.execute 用模型跑推論，得到結果 r.result
  4. ④ 生成證明：prove 步驟用 proving.key 和計算過程，產出零知識證明 π
  5. ⑤ 驗證階段：Verifier（V）收到 π 後，用 verification.key 驗證，確認無誤後可 commit 結果
  6. ⑥ 迴圈：若有多輪互動或批次處理，可回到 ① 繼續

八、歷史時間線

時間線解讀

此圖呈現 ZKML 領域的研究發展脈絡，時間從左上角開始（2017）沿箭頭方向前進。

  • 2017 SafetyNets：首篇將 DNN 放進可驗證計算的論文，開啟這個領域
  • 2020 年：ZKDT、vCNN 等多篇論文出現，探索不同模型架構的 ZK 證明
  • 2021 年：zkCNN、ZEN、VeriML 等重要工作，逐漸系統化
  • 2024 年：爆發式成長，ZKML、zkLLM 等開始挑戰大型語言模型

趨勢：從「能不能做」到「怎麼做得更好」，從小模型到大模型。

年份 論文 主要貢獻
2017 SafetyNets 把 DNN 表成算術電路，用互動式證明驗證（強調 verifiable，不一定 ZK）
2020 ZKDT 決策樹的 ZK 預測證明，首次提出「準確度證明」概念
2020 Polynomial Approx. 研究用低次多項式替代 ReLU，分析精度損失
2021 ZEN 編譯器化，ZENinfer（推論）+ ZENacc（準確度）
2021 zkCNN FFT Sumcheck，首次讓 VGG-16 可驗證推論變得實際可行
2024 ZKML (EuroSys) 自動化配置優化，建立精確成本模型，從「能不能做」到「怎麼做得好」

架構說明

這張圖展示 zkCNN 如何處理一個典型的 CNN 網路：

  • 輸入：X（影像輸入）、W（模型權重）、Bit-decomposition（位元分解輔助值）
  • 主要流程：輸入經過多層「Convolution → ReLU + Max pooling」的堆疊，最後到 Fully connected 層輸出
  • 關鍵設計：右側的 Bit-decomposition 連接到每個 ReLU 和 Max pooling 層——這些非線性操作需要額外的位元分解來做範圍證明

zkCNN 的突破：用 GKR 協定 + FFT Sumcheck 加速卷積層驗證，讓 VGG-16 等級的模型首次變得實際可行。

九、設計空間總結

分類樹解讀

這張圖用樹狀結構把現有 ZKML 論文做分類，從左到右展開：

三個分析維度

證明目標

  • 推論正確性：輸入 x → 輸出 y
  • 模型性質：準確度達標

隱私目標

  • Type A：保護輸入
  • Type B：保護模型
  • Type C：兩者都保護

算術化策略

  • 量化（float → int）
  • 多項式近似
  • 位元分解
  • 查表 (Lookup)

論文定位對照

論文 證明目標 隱私覆蓋 算術化策略
SafetyNets Inference Verifiable (non-ZK) 量化
ZKDT Inference + Accuracy Type B 比較 gadget
zkCNN Inference + Accuracy Type A/B 可選 GKR + Sumcheck
ZEN Inference + Accuracy Type A/B 可選 編譯器自動選擇
ZKML Inference + Audit Type A/B 可選 Lookup + 自動優化

十、早期瓶頸與未來方向

三大瓶頸

非線性太貴

ReLU/MaxPool/Softmax 的比較操作成本極高，佔電路很大部分

語義差異

你證明的是量化後的模型，不是原始 float32 模型

規模限制

現有系統最多處理幾千萬參數，LLM 有幾十億～幾千億參數

未來研究方向

  • 更好的算術化：更有效率的 lookup 協定、更聰明的位元分解策略
  • 硬體加速：GPU / 專用晶片加速證明生成
  • 更大模型：zkLLM 探索 Transformer 架構
  • 實際部署：區塊鏈智能合約、隱私保護 ML-as-a-Service

結語：三個 Takeaways

1. 核心轉換

ZKML 把 ML 推論轉換成有限域上的算術約束，讓 Prover 證明正確性而不洩漏敏感資訊

2. 早期突破

圍繞「怎麼便宜地處理非線性操作」與「怎麼把工作自動化、系統化」

3. 差異維度

不同論文的差異可從三個維度理解：證明目標 × 隱私目標 × 算術化策略
