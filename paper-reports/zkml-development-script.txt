ZKML 發展脈絡 口頭報告講稿

各位好，今天我要報告的主題是「ZKML 發展脈絡：從可驗證計算到零知識機器學習」。這不是單一論文的報告，而是一個技術綜述，幫助大家理解 ZKML 這個領域是怎麼演進過來的。

我會從一個故事開始，然後講核心概念、技術挑戰、重要論文，最後做一個設計空間的總結。

好，讓我先從故事開始。

第一部分：為什麼需要 ZKML？

想像一個場景。你是一家醫院，想用雲端 AI 服務來分析病人的 X 光片。你把影像上傳，雲端回傳一個診斷結果。

這裡有兩個問題。

第一個問題是：你怎麼知道雲端真的用了它宣稱的那個高準確度模型？它可能偷偷換了一個便宜的小模型來省錢，反正你也看不出來。這叫做「正確性問題」或「誠實性問題」。

第二個問題是：病人的 X 光片是隱私資料，雲端服務商不應該看到。但你又需要它幫你算。這叫做「隱私問題」。

這兩個問題，就是 ZKML 要解決的。

ZKML，全名是 Zero-Knowledge Machine Learning，零知識機器學習。它的目標是：讓你可以驗證 AI 推論的正確性，同時保護敏感資料不被洩漏。

用一句話來總結 ZKML 的核心：

把 ML 推論或評估寫成有限域上的算術約束，讓 Prover 能在不洩漏敏感資料的情況下，證明推論或模型性質正確。

這句話很重要，我等一下會拆解。

第二部分：先搞清楚兩個概念

在講 ZKML 之前，我要先區分兩個容易混淆的概念。

第一個是「可驗證計算」，英文叫 Verifiable Computation。它的重點是「算對沒」。Verifier 可以確認 Prover 正確執行了計算，但不一定隱藏任何資訊。

第二個是「零知識」，英文叫 Zero-Knowledge。它的重點是「算對，而且不洩漏 witness」。除了計算正確外，Verifier 不會獲得任何額外資訊。

為什麼要區分這兩個？因為早期很多工作是先把「可驗證」做出來，之後才把「零知識」的性質補上。這是歷史演進的脈絡。

換句話說，ZKML 不是一開始就有的，它是從可驗證計算慢慢演化過來的。

第三部分：三種隱私需求

ZKML 的應用場景可以分成三種，根據「誰的資料要保護」來分：

Type A：公開模型，私密輸入。這就是剛才醫院的例子。模型是公開的，但病人資料要保護。

Type B：私密模型，公開輸入。比方說你是一家 AI 公司，模型是你的商業機密，但客戶的輸入可以公開。你要證明你真的用了某個模型，但不想透露模型權重。

Type C：模型和輸入都是私密的。這是最難的情況。比方說金融風控，模型是銀行機密，客戶資料也是隱私，但你還是要證明推論正確。

後面講每篇論文的時候，我都會標明它屬於哪一種類型。

第四部分：密碼學抽象 — Prover 和 Verifier

現在進入技術部分。

ZKML 的架構有兩個角色。

Prover，證明者。他拿到輸入 x，可能也拿到模型 f，計算出結果 y 等於 f(x)，然後產生一個證明，我們用希臘字母 pi 來表示。

Verifier，驗證者。他只看公開資訊和證明 pi，就能驗證計算是否正確。他不需要重算一次。

這裡有三個關鍵術語要記住：

Statement，就是公開的資訊。可能是輸出 y、模型的承諾、輸入的承諾。

Witness，就是私密的資訊。可能是輸入 x、模型參數、中間計算值。

Relation，就是要滿足的約束關係。R(statement, witness) = 1 當且僅當計算正確。

這三個詞在後面會一直出現，務必記住。

第五部分：工程核心 — 算術化

好，現在進入最關鍵的技術問題：算術化，英文叫 Arithmetization。

問題是這樣的：ZK 證明系統擅長處理加法和乘法。但機器學習模型有浮點數、除法、比較、ReLU 等等，這些都不是加法乘法。

怎麼辦？我們需要把 ML 模型「翻譯」成 ZK 能處理的形式。這個翻譯過程就叫算術化。

第一步是量化。把 float32 變成整數或定點數。比方說乘以 2 的 16 次方再取整數。這樣推論就變成整數乘加，ZK 可以處理。

量化公式是：q 等於 round(r 除以 S) 加 Z。其中 r 是實數值，S 是 scale，Z 是 zero-point，q 是量化後的整數。

但這裡有一個很重要的問題。ZK 系統在有限域上運算，有限域的數字會「繞回來」，這叫 wrap-around。比方說在模 p 的有限域，如果數字超過 p，它會從 0 重新開始。

這會造成什麼問題？如果你的量化值不小心溢位了，它會變成一個看起來合法但完全錯誤的值。

所以我們需要額外的 range constraints，範圍約束，來確保數值落在預期範圍內。這就是為什麼後面會講到 bit-decomposition 和 range-check 這些技術。

第六部分：線性層 vs 非線性層

量化之後，神經網路的運算可以分成兩類。

第一類是線性層，包括全連接層和卷積層。全連接就是 y 等於 Wx 加 b，卷積可以展開成很多點積。這些都只需要乘法和加法，對 ZK 來說相對友善。

第二類是非線性層，這是早期最大的瓶頸。包括：

ReLU：max(0, x)，需要比較 x 和 0 誰大
MaxPool：比較多個元素選最大
Softmax：有指數函數和除法
Argmax：找最大值的索引

這些操作在有限域上都很難處理。

第七部分：三大解法

早期 ZKML 研究發展出三種主要解法來處理非線性：

第一種是多項式近似。把 ReLU 換成一個低次多項式，比方說二次函數。這樣只剩加法乘法，ZK 可以處理。缺點是：你改變了模型的語義。你證明的不再是原本的 ReLU 網路，而是一個「近似版」。

第二種是範圍證明和位元分解。把每個數字分解成 k 個位元，然後用位元來做比較。比方說判斷 x 是正是負，就看最高位元是 0 還是 1。缺點是：每個數字需要 O(k) 個額外約束，成本很高。

第三種是查表，英文叫 Lookup。預先計算好一張表，比方說 ReLU 在 -128 到 127 的所有輸出值，然後證明你的結果在這張表裡面。缺點是：表格大小有限制，不能無限大。

這三種方法各有優缺點，後面的論文會用不同的組合。

現在我要講一個非常重要的認知：

ZK 保證的是你定義的 relation 的正確性。但如果你用多項式近似或量化，relation 的語義本身就變了。

這不是 bug，這是 ZKML 設計必須面對的 trade-off。你證明的東西，跟原本的 float32 模型可能有些許差異。你需要在「證明效率」和「語義精確度」之間做取捨。

第八部分：發展時間線

好，技術背景講完了，現在來看歷史發展。

2017 年，SafetyNets。這是 ZKML 思想的起點之一。它把 DNN 推論表示成算術電路，用互動式證明來驗證。但它主要強調「可驗證」，不一定是零知識。

2020 年，ZKDT，全名是 Zero Knowledge Decision Tree。這是第一次明確喊出「ZK 加 ML」。它對決策樹做 ZK 預測證明，而且首次提出：ZK 不只可以證明單次推論，也能證明統計性性質，比方說準確度。

同年 2020 年，有一篇研究多項式近似的論文。專門研究用低次多項式替代 ReLU，討論怎麼設計多項式能減少準確度損失。

2021 年，ZEN。這是第一個「編譯器化」的嘗試。它把「怎麼把 NN 變成 ZK 電路」這件事做成一個 compiler pipeline。ZEN 有兩個子系統：ZENinfer 證明推論正確，ZENacc 證明模型準確度。

同年 2021 年，zkCNN。這是 CNN 領域的里程碑。它設計了一個線性時間的 FFT sumcheck，第一次讓 VGG-16 這種大型 CNN 的可驗證推論變得實際可行。

2024 年，ZKML，發表在 EuroSys。這是系統優化的集大成者。它建立精確的 cost model，自動選擇最佳的電路參數，包括 logrows、lookup_bits 等等。根據論文 Table 2-3 的評估，在 MobileNet、ResNet 等模型上，使用 EZKL 和 halo2 後端，證明時間減少 3 到 10 倍，記憶體使用減少 2 到 5 倍。當然，實際提升幅度取決於模型規模和參數配置。

第九部分：里程碑論文詳解

現在我用一個統一的框架來分析每篇里程碑論文。這個框架有六格：Problem、Threat Model、Statement/Witness/Relation、Arithmetization、Key Innovation、Limitation。

首先是 SafetyNets，2017 年。

Problem：雲端推論不可信，客戶想要「算對的證明」。
Threat Model：不信任雲端，要保證計算正確性。
它不太強調隱私，主要是可驗證。
Key Innovation：把 DNN 表示成算術電路，用互動式證明。
Limitation：強調 verifiable，不一定是零知識；對模型類型有限制。

SafetyNets 的歷史定位是：它展示了 DNN 推論可以被形式化並被驗證，是後續 ZK 版推論證明的基礎脈絡。

接著是 ZKDT，2020 年。

Problem：證明決策樹預測正確，且可證明模型準確度。
為什麼從決策樹開始？因為它的計算結構離散，路徑可以用比較描述，比較容易做 ZK protocol 設計。
Key Innovation：首次提出兩類證明。R_infer 證明預測正確，R_acc 證明準確度達標。
隱私覆蓋：Type B，模型隱私。

ZKDT 最重要的貢獻是：它告訴我們 ZK 不只能證明單次推論，也能證明統計性性質。

然後是 zkCNN，2021 年。

Problem：CNN 比決策樹難很多。乘加多，非線性多，pool 和 activation 的比較更痛。
Key Innovation：設計了 Sumcheck for FFT，把 prover 時間從 O(N log N) 降到 O(N)。這讓證明 FFT 比直接計算還快。
隱私覆蓋：Type A 和 Type B 都可以支援。
模型通用性：限於 CNN 結構。
Limitation：只支援 CNN，不支援 Transformer；證明大小比較大。

zkCNN 是 ZKML 領域的里程碑，首次讓大規模 CNN 的可驗證推論變得實際可行。

再來是 ZEN，2021 年。

它的定位是：從手工 protocol 邁向 compiler。
兩個子系統：ZENinfer 證明推論正確，ZENacc 證明模型準確度。
編譯器做的事包括：模型表示、電路生成、優化。
隱私覆蓋：Type A 和 Type B 可選。
模型通用性：General DNN。

注意一點：ZENacc 證明的是「在特定測試集上達到某準確度」，不是對所有輸入的保證。這很容易被誤解，報告時要講清楚。

ZEN 的歷史意義是：讓 ZK 加 NN 從研究原型往工程系統走，開始把「生成和優化」當成第一級問題。

最後是 ZKML，2024 年 EuroSys。

Key Innovation：自動化參數調優，建立精確 cost model，支援多種後端。
它的核心理念是：讓使用者不需要手動調參，系統自動找到最佳配置。
隱私覆蓋：Type A 和 Type B 可選。
模型通用性：General DNN。

ZKML 代表了 ZKML 領域從「能不能做」走向「怎麼做得好」的轉變。

第十部分：設計空間總結

現在讓我把這些論文的差異收斂成一個框架。

ZKML 研究可以從三個維度來分析：

第一個維度是證明目標。你到底要證明什麼？

Inference Correctness：單次推論正確。對輸入 x，模型輸出確實是 y。

Model Properties：模型性質，比方說準確度。模型在測試集上達到宣稱的準確度。

第二個維度是隱私目標。你要保護什麼？

輸入隱私：保護使用者資料。
模型隱私：保護模型權重。
架構隱私：保護模型結構。

不同的應用場景需要不同的隱私組合。

第三個維度是算術化策略。你用什麼方法把 ML 變成 ZK 電路？

量化：float 轉 int，大幅降低複雜度，但有精度損失。
多項式近似：只剩加乘，但改變模型語義。
Range-check：保留原始語義，但成本較高。
Lookup：保留語義、效率較好，但表格大小有限制。

不同論文用不同的組合。SafetyNets 用量化，ZKDT 用比較 gadget，zkCNN 用 GKR 加 Sumcheck，ZEN 用編譯器自動選擇，ZKML 用 Lookup 加自動優化。

第十一部分：早期瓶頸

總結一下早期 ZKML 面臨的三大瓶頸：

第一，非線性太貴。ReLU、max、softmax 的比較操作在 ZK 電路中成本極高。

第二，語義差異。量化會改變語義，你證明的是量化後的模型，不是原本的 float 模型。

第三，規模爆炸。電路和約束的規模隨模型規模快速成長，特別是在大量 bit-decomposition 或 range-check 的策略下，成本會陡增。

這些瓶頸推動了後續的研究方向：更好的算術化方法、更高效的證明系統、以及自動化的編譯器。

第十二部分：未來方向

最後講一下未來方向。

第一是更大的模型。目前的研究主要在 CNN，未來會往 Transformer、LLM 發展。zkLLM 已經在做這件事了。

第二是更快的證明。包括硬體加速、GPU 並行化、更高效的證明系統。

第三是更好的工具。自動化編譯器、更友善的開發體驗、跟現有 ML 框架的整合。

第四是實際部署。區塊鏈 AI 應用、隱私保護 ML-as-a-Service、可驗證的 AI agent。

第十三部分：三個 Takeaways

總結三個 takeaways：

第一，ZK 乘 ML 的核心是把推論或評估變成有限域算術約束的 relation。

第二，早期突破多圍繞「怎麼便宜地處理非線性和比較」以及「怎麼把工作系統化」。

第三，不同論文的差異主要在：證明目標乘隱私目標乘算術化策略。這三個維度。
